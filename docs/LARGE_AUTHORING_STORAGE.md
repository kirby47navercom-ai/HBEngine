# 큰 제작 데이터의 저장과 자동화

자동화 폴링은16MiB까지 받고, 단일 결과는14MiB까지 인코딩해요. 이전 폴링 경로의4MiB를 넘는 정상 문서 응답이 무한 재시도하다120초 후 만료되던 문제를 수정했어요. 완료 결과는 한 번 JSON으로 만들고 원본 결과 객체 대신 문자열을 대기열에 보관해요. 여러 결과는 바이트 한도와50개 한도에 맞춰 FIFO로 나눠 보내요. 너무 큰 단일 결과는 `RESULT_TOO_LARGE`로 즉시 알리고, 시퀀스 키는 `sequence.keys.read`의 페이지 조회를 사용해요. 다른 에셋은 아래 document.read로 필요한 하위 항목을 조회해요. 하나의 거대한 문자열/바이너리 값 자체를 조각내어 보내는 기능은 별도예요.

기존 타이머 하나를 사용하며 작업 중에는 빠르게 결과를 비우고, 명령 처리8ms 또는 대기 인코딩8MiB에서 다음 회차에 양보해요. 실패한 네트워크는 기존500ms 재시도 간격을 유지해요. 대기 문자열은8MiB 미만에서 최대14MiB 결과 하나를 더할 수 있으므로22MiB 미만이고 전송 본문·임시 인코딩·서버/문서 객체 메모리는 별도예요. 종료 후 늦게 끝난 명령의 결과와 남은 명령은 보관하지 않아요.

프로젝트 복구의 주 저장소는 `Saved/Editor/storage.json`의 현재 파일 하나예요. 원래v1형식과 프로젝트ID 분리·원자적 임시 파일 전환을 유지하고 용량 예산을32MiB로 확장했어요. 브라우저 localStorage는 작은 값의 선택적 보조 백업이에요. 키와 값의 UTF-16 크기가256KiB를 넘으면 그 보조 사본을 만들지 않고, 이전 보조 값도 지워 오래된 편집본으로 잘못 복원하지 않아요. 보조 백업의 할당량 실패는 주 디스크 저장 실패로 표시하지 않아요. 주 디스크의 오류는 그대로 보고해요.

일반 저장은 에셋 파일을 먼저 확정하고 복구 상태 flush도 기다려요. 파일 저장은 성공했지만 복구 flush가 실패하면 파일 성공을 취소한 것으로 보고하지 않고 별도 로그를 남겨요. `editor.storage.flush`는 복구 상태만 디스크에 반영하고 `pending`, `backupSkipped` 등 진단을 돌려줘요. 기존 창 종료와 프로젝트 전환의 flush 경로도 유지해요. 강제 종료 직전의 모든 미저장 입력까지 보장하는 뜻은 아니에요.

에셋 저장 요청은 원본 비교 기준과 새 문자열을 함께 담으므로32MiB까지 받아요. 외부 파일 변경 비교는 유지해요. 유효한 JSON 에셋의 의미가 같거나 일반 텍스트 바이트가 같으면 원본을 다시 쓰거나 백업을 추가하지 않아요. 실제 변경은 기존처럼 정확한 이전 원본을 백업해요. 다중 파일 트랜잭션의 기존8MiB 예산을 함께 늘리지는 않았고, 이전의 사용자 백업을 일괄 삭제하지도 않아요.

검증은 격리된 프로젝트의9MiB 주 복구 데이터 재시작, 강제로 제한한 보조 저장소, 65,536키 원본/변경/무변경 저장과 충돌, 실제 창의 큰 전체 응답·부분 조회·저장·복구 flush·재생을 사용했어요. 사용자 프로젝트·프로필은 검사에 사용하지 않았어요.

## 모든 문서의 부분 조회

`document.read`는 모든 열린 에셋에 `pointer`, `offset`, `limit`로 접근해요. 기본은 값 전체 대신 형태·크기와 짧은 id/name만 주며 `values=true`에서 선택한 항목의 값을 복사해서 줘요. 배열의 key는 원래0부터 시작하는 인덱스, 객체는 저장된 속성 순서예요. `nextOffset`으로 이어 읽어요. 원본·dirty·revision·Undo는 바꾸지 않으며 선택적 expectedRevision은 오래된 읽기를 거절해요.

예를 들어 씬에서 pointer=/objects,values=false로 오브젝트 목록과ID를 확인하고, pointer=/objects/42,values=true로 하나의 속성을 읽어요. 시퀀스에서도 /tracks/0/keys를 페이지로 읽을 수 있어요. 없는 속성·배열의01/- 등 잘못된 인덱스·잘못된 이스케이프는 거절해요. 경로는 [RFC6901의 Syntax/Evaluation](https://www.rfc-editor.org/info/rfc6901/)을 대조한 JSON Pointer이며 ~1을/로, ~0을~로 이 순서로 풀어요. JavaScript 상속 멤버는 따라가지 않아요. URI fragment, 원문 중복 키 검출이나 큰 문자열의 범위 읽기를 구현했다고 주장하지 않아요.

작은 스키마 조회는 `node tools/hb.mjs schema --section documentQuery` 또는 `--section sequenceKeyStorage`를 써요. 전체 API JSON과 전체 문서를 매번 출력할 필요가 없어요.
