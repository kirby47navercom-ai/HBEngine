# 106 — 교차점 머테리얼·UV·법선·마스크

경로 추적과 기하 GI가 삼각형 중심의 단색을 사용하던 경로를 각 광선 교차점의 재질 계산으로 바꿔요. 실제 UV와 부드러운 법선, 텍스처·프로시저럴 그래프, 투명 마스크와 접선 공간 법선맵을 D3D11·WebGL2·WebGPU에 연결해요. 기존 105의 누적 경로 추적과 색 투과 그림자를 유지해요.

## 제작과 실행

기존 머테리얼 그래프·함수·레이어·인스턴스 파라미터를 사용해요. 색·불투명도, 발광·두께, 금속성·거칠기·투과율·굴절률, 법선, 흡수 색·거리를 교차점에서 평가해요. 마스크 기준보다 낮은 알파는 광선 교차에서 제외해요. 그림자 광선과 발광체 샘플도 해당 지점의 재질을 사용해요.

UV·시간·위치·법선·시선, 산술·보간·채널·벡터·정규화·Fresnel·노이즈·체커·그라디언트·패너·UV 회전을 포함하는 50개 내부 연산으로 기존 제작 그래프를 낮춰요. 정적 계산은 상수로 접고 마지막 사용이 끝난 임시 레지스터를 재사용해요. C++·블루프린트·AI가 별도 셰이더 코드를 작성할 필요는 없어요.

```cpp
hb::Materials::SetFloat(target, "Shift", .25f);
hb::Components::SetBool(post, "PostProcessVolume", "pathTracingEnabled", true);
```

UV가 움직이거나 재질·텍스처·포즈가 바뀌면 BVH/재질 데이터와 누적 이력을 갱신해요. 프로그램의 구조가 같으면 상수 변경만으로 셰이더를 다시 만들지 않아요. 유효한 정수 명령·자료형·참조를 검사한 뒤 엔진이 관리하는 연산으로 셰이더를 생성해요. JSON에서 임의 셰이더 문자열을 받아 실행하지 않아요. 생성 헤더는 Git에서 제외하고 네이티브 검사·데스크톱 빌드가 원본 연산에서 자동 생성해요. 배포본에는 생성 결과와 SHA를 포함해요. 저장소 밖에서 도구를 실행해도 생성 대상은 해당 엔진 폴더예요.

2D·큐브·배열·볼륨 텍스처의 원본 RGBA 데이터와 UV 행렬·랩·flipY, nearest/linear 샘플링과 sRGB 변환을 연결해요. 교차점 검사의 실제 이미지 픽셀 증거는 2D 텍스처·법선·마스크에 해당해요. 배열·볼륨·큐브는 이번 광선 경로에서 데이터 포장까지 확인했고, 기존 래스터 경로의 실제 가족별 픽셀 검사는 유지했어요. 광선 텍스처의 mip/LOD·비등방 필터링·볼륨 wrapR는 별도 작업이에요.

## 구현과 비용

- 삼각형당 UV·법선·머테리얼 주소 80바이트를 기존 광선 레이아웃에 더해요. 머테리얼당 기본/프로그램 메타데이터 160바이트, 명령당 48바이트, 텍스처당 헤더 64바이트와 원본 RGBA float 픽셀당 16바이트를 사용해요. GPU 이미지 패딩과 기존 BVH·이력 자원은 별도예요.
- 광선 프로그램은 구조별 실제 셰이더 함수로 생성해요. 사용 필드·텍스처 종류를 특수화하고 경로 추적 전용 패스에서 관련 없는 후처리 계산을 제외해요. 네이티브는 기존 8×8 컴퓨트와 세 프레임 상수 버퍼를 유지해요.
- 반복문은 기존 탐색 예산을 유지하고 실제 입력으로 한정해요. 네이티브 `[fastopt] [loop]`, WebGPU 공유 함수는 불필요한 컴파일 확장을 줄여요. 장면 오브젝트 수 제한을 추가하지 않았어요. 64개 동시 임시 값·필드당 4096개 명령은 그래프 셰이더 예산이며 오브젝트 개수 제한과 달라요.
- 기본 경로 추적/GI 비활성 시 광선 데이터를 할당하지 않고 끄면 해제해요. 원본 이미지의 CPU 디코드는 캐시해요. 실제 기하·시간·재질 변경은 CPU BVH와 float 이미지를 다시 만들므로 큰 동적 장면의 비용은 남아 있어요. 렌더 결과의 자동 GPU→CPU 읽기는 추가하지 않았어요.

## 수정한 실행 오류

설치된 Three r180의 `UniformsGroup.updateVector4`는 네 번째 값과 `offset+4`를 비교해요. 옆 uniform 값과 새 `w=0`이 같으면 이전 GPU 값이 남아 누적 샘플 초기화가 실패했어요. 실제 업로드 추적과 설치 클래스의 독립 재현으로 확인하고 r180에만 적용하는 공용 바인딩 호환 처리를 추가했어요. 의존성 파일은 수정하지 않았어요. 프로그램 구조가 바뀌면 WebGL 머테리얼의 이전 프로그램 참조도 해제해요. 파라미터 값만 바뀌면 같은 프로그램을 재사용해요. Three 버전을 바꿀 때 내부 바인딩 API와 이 보정의 필요성을 다시 확인해야 해요.

초기 범용 그래프 인터프리터가 컴파일러에서 중첩 확대된 문제는 직접 프로그램·고정 필드 함수·샘플러 특수화로 해소했어요. 검사의 시간 제한이나 픽셀 통과 기준을 늘리거나 낮추지 않았어요. 네이티브 기본/후처리는 각 프로세스의 기존 120초 제한으로 나눠 같은 검증 항목을 모두 실행해요. 색 검사에서 과도한 발광과 ACES 톤매핑이 채널 차이를 줄이는 문제는 발광 보정값을 낮춰 확인했어요. 다른 장면·통과 기준은 유지했어요.

## 증거와 경계

[기계 검사 기록](research/RENDERING_106.json)에 공용 계산·스키마·AI·생성 파일 검사, 실제 세 Windows 실행기와 네이티브 하드웨어 결과를 기록해요. 106의 실제 픽셀 검사는 UV/텍스처, C++ 파라미터 변경 후 누적 초기화, 알파 교차 제외, 법선맵, 체커를 포함해요. 098–105 회귀, 2D·파티클·그림자·변형·자원 해제도 유지해요. 설치는 [설치 영수증](research/USER_INSTALL_106.json)에 별도로 기록해요.

닫힌 고체·중첩 매질 스택, HDRI 중요도 샘플링·대기/볼륨 광수송, 정확한 코팅·피부·모발 경로 로브, 디노이저·caustics는 이번 변경에 포함하지 않아요. 래스터 그림자맵은 여전히 깊이 기반이에요. 광선 BVH에는 2D 스프라이트와 임의 GPU 변형이 포함되지 않아요. 광선 정점 색 보간과 비표준 스킨 shear의 정확한 법선도 별도 경계예요. 전체 게임 FPS·RAM/VRAM·실제 휴대폰 성능은 이번 검사로 보증하지 않아요.

## 읽은 근거

- [PBRT 상호작용](https://www.pbr-book.org/4ed/Geometry_and_Transformations/Interactions)의 점·기하/셰이딩 법선·UV 구역, [삼각형 메시](https://www.pbr-book.org/4ed/Shapes/Triangle_Meshes)의 지정 보간 구역을 읽었어요. 연결된 구현/API와 나머지 본문은 미독으로 유지해요.
- [Three Texture](https://threejs.org/docs/pages/Texture.html)의 `transformUv/updateMatrix` 지정 구역, 설치 r180의 RTT·NodeFrame·NodeUniform·Bindings·ACES 구역을 대조했어요. 현재 문서와 설치 버전의 전체 동등성을 주장하지 않아요.
- [r180 UniformsGroup 원본](https://raw.githubusercontent.com/mrdoob/three.js/r180/src/renderers/common/UniformsGroup.js)의 Vector4 비교를 읽고 설치 클래스의 동일 동작을 재현했어요.
- [Microsoft HLSL for](https://learn.microsoft.com/en-us/windows/win32/direct3dhlsl/dx-graphics-hlsl-for)의 loop/fastopt 본문, 공식 ANGLE `ShaderD3D/OutputHLSL/Renderer11` 지정 컴파일 구역을 읽었어요. ANGLE main 관찰 자료를 이 PC의 설치 ANGLE 버전으로 간주하지 않아요.

16개 원문/설치 소스 snapshot의 SHA와 읽은 구역을 남겨요. 전체 Unity·Unreal 본문/API 분석 gate와 남은 엔진 기능의 완료를 대신하는 기록은 아니에요.
