# 파일 이름 변경 복구

`ProjectService.rename`의 Assets/Source/Settings 일반 파일 이름 변경은 원본 파일과 모델 `.import.json`을 같은 기록으로 처리해요. 파일 내용·안정 에셋 ID·리다이렉트를 함께 다루고, 미완료 기록은 프로젝트 인덱스를 읽기 전에 복구해요. 폴더/특수 내부 경로의 이름 변경은 이전 경로를 유지하며 이 저널의 내구성 범위에 포함하지 않아요.

바이너리 본문을 JSON이나 백업 파일로 복제하지 않아요. 스트리밍 SHA-256과 파일 식별자를 기록하고 같은 볼륨의 배타적 하드링크 생성 뒤 원래 이름을 제거해요. 지원하지 않는 파일시스템·권한이면 실패하며, 덮어쓰는 이동으로 우회하지 않아요. 각 제거 직전에 양쪽 파일의 해시와 식별자를 확인해서 외부 파일이 바뀌면 마지막 원본을 지우지 않아요. 실제 전원 차단·모든 파일시스템·동시 프로세스 잠금을 검증한 방식은 아니에요.

`Saved/Renames`의 미완료 기록에는 경로·해시와 인덱스/리다이렉트의 전후 텍스트가 있어요. 완료·롤백·해결된 기록은 해당 경로·ID·해시 요약으로 압축해서 전체 프로젝트 인덱스를 이름 변경마다 쌓지 않아요. 압축 실패는 이미 확정된 이동을 되돌리지 않고 경고를 보존하며 다음 열기에 재시도해요. 준비 기록은 32 MiB까지예요. 이 제한은 바이너리 파일 크기 제한이 아니며, 큰 파일의 해시 I/O와 임시 메타데이터 비용은 남아 있어요.

## 사람과 AI의 선택

기존 **저장 묶음 복구** 창과 `project.recovery.inspect/resolve`를 사용해요. ID는 `rename:UUID`이며 원래 경로에서 새 경로로의 이동과 양쪽 현재 파일의 실제 해시·크기를 표시해요. 본문은 응답에 넣지 않아요. 기본 32행, 최대 128행이며 `expectedRevision`은 페이지 밖 파일·식별자·기록·메타데이터까지 확인해요.

- `before`: 묶음 전체의 원래 이름 복구예요. 원본 해시와 파일 식별자를 확인할 수 있을 때만 적용해요. 원본 본문 백업을 꾸며내지 않아요.
- `after`: 현재 내용을 보존하면서 새 이름으로 정리해요. 아직 옛 이름에만 있는 사이드카도 함께 옮겨요.
- `disk`: 현재 내용·삭제·위치를 보존하고 해당 범위의 에셋 ID와 리다이렉트를 정리해요. 다른 경로의 외부 메타데이터도 유지해요.

모든 이름 변경 행에 명시적 선택이 필요해요. 원래 이름과 새 이름에 서로 다른 파일이 모두 있거나 안정 ID가 중복되면 자동으로 덮어쓰지 않아요. 별도 이름으로 파일을 보존하거나 중복 ID를 정리한 다음 다시 선택해야 해요. 미리보기도 이 적용 가능성을 검사하며 파일을 바꾸지 않아요.

선택을 적용할 때도 현재 디스크 기준의 자식 기록을 만들어요. 중간 종료는 그 기준으로 되돌리고 원래 충돌을 남겨요. 확정된 자식은 부모 결정을 마무리해요. 자식에 다시 충돌이 생기면 원래 묶음 전체 범위를 유지하고 자식부터 선택해요. 콜백 실패 후에도 같은 프로젝트에서 다시 시도할 수 있어요.

이름 변경 충돌 중에는 인덱스 자동 저장과 다른 디스크 복구를 보류해요. 읽기·목록·복구 조회는 가능하며, 해결 뒤 기존 텍스트/바이너리·WriteIntent 복구를 이어가요. 일반 문서 Undo와는 별개예요. 전체 디렉터리 이동, 임의 스트림 교체, 다른 볼륨의 이동, 외부에서 기록을 제거·파손한 경우와 물리적 파일시스템 내구성은 추가 작업이에요.

검사 도구는 `tools/check-rename-journal-2676.mjs`예요. 실제 소유 파일/ProjectService·소유 Node 프로세스 강제 종료·연결된 복구 재시작·ID/CAS·미리보기·사람 DOM·파일 교체 경합을 검사해요. 10,000개 무관 인덱스 항목이 있어도 완료된 두 경로의 기록이 4 KiB 미만인 소유 표본을 확인했어요. 전체 프로젝트 성능·GUI·하드웨어 전원 차단 증명은 아니에요.
