# DirectX 셰이더 재실행 캐시 · 346–350

DirectX 게임을 다시 실행하거나 다른 프로젝트를 열 때 같은 HLSL을 매번 FXC로 컴파일하던 비용을 줄였어요. 래스터·노드 머테리얼·화면 효과·파티클 렌더/정렬·Bloom·Hi-Z·광원 타일·프로브 필터가 하나의 디스크 저장소를 써요.579에서는 [일반 Compute 커널](COMPUTE_KERNEL_CACHE_579.md)도 연결했어요. WebGL/WebGPU 드라이버 파이프라인은 이 저장소를 쓰지 않아요.

기본 저장 위치는 `%LOCALAPPDATA%/HBEngine/Cache/ShaderBytecode`예요. 게임별 소리·입력·저장 데이터는 공유하지 않고, 기기와 무관한 컴파일 결과만 재사용해요. `HB_USER_DATA_DIR`을 명시한 검사는 그 디렉터리의 `Cache/ShaderBytecode`로 격리해요. SDK는 `hb::gpu::SceneRenderer::configureShaderCache(directory)`를 호출하기 전에는 디스크에 접근하지 않아요. 빈 경로로 끌 수 있어요.

저장소 전체의 소유 바이트코드와 게시 중 임시 파일을 합쳐 8 MiB 안에서 관리해요. 교체 파일도 임시 파일의 예산에 포함하고 오래 쓰지 않은 항목부터 지워요. 두 작은 식별/잠금 파일의 내용과 파일시스템 메타데이터는 바이트코드 예산 밖이에요. Versions별 저장소를 만들지 않아요. 모르는 파일·잘못된 식별 파일·링크를 일괄 삭제하지 않아요.

재사용 키에는 최종 HLSL 전체, 진입점, 대상 프로필, 컴파일 옵션, 실제 로드한 컴파일러 DLL의 크기/수정 시각을 넣어요. 파일명 해시가 일치해도 저장된 키 전체를 다시 비교해요. 길이·버전·내용 체크섬을 검사하고, 허용 크기를 넘는 헤더는 할당 전에 거부해요. 체크섬은 손상 감지용이며 서명이나 실행 파일 인증 체계가 아니에요.

읽기 실패·용량 초과·쓰기 실패·다른 프로세스의 잠금은 원본 컴파일로 이어져요. 캐시 바이트코드를 D3D 장치가 거부하면 그 항목을 버리고 한 번 다시 컴파일해요. 원본 HLSL이나 장치 자체의 오류는 정상적으로 보고해요. [CreateComputeShader](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-createcomputeshader)의 컴파일 바이트코드 입력과 [D3DCompile](https://learn.microsoft.com/en-us/windows/win32/api/d3dcompiler/nf-d3dcompiler-d3dcompile)의 소스·진입점·프로필·옵션 계약을 대조했어요.

여러 프로세스의 게시에는 즉시 반환하는 파일 범위 잠금을 써요. 잠금을 얻지 못하면 기다리지 않아요. 게시 중 종료되면 운영체제가 잠금을 풀고, 다음 게시가 소유 임시 파일을 정리해요. 완료 파일은 임시 기록/flush 뒤 교체해요. 이 계약은 [LockFileEx](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-lockfileex)의 비대기 플래그와 종료 후 잠금 해제 설명을 참고했어요.

기존 `shaderCompilation` 9개 필드의 순서는 유지했어요. `shaderDiskCache`에 적중·실패·저장·퇴출·최근 검사 바이트·예산·거부·오류·경합·활성 상태를 별도로 보내요. 준비된 프로그램을 그대로 쓰는 프레임이나 진단 조회는 디렉터리를 다시 읽지 않아요. `lastScannedBytes`는 마지막 검사 값이며 다른 프로세스가 이후 바꾼 내용을 실시간으로 재는 값이 아니에요. 사람용 프로파일러와 AI 조회는 같은 진단을 읽고 `hb schema`의 `nativeShaderCache`가 위치·예산·실패 동작을 설명해요. 개발용 플레이어의 `hbPlayerDebug.inspect().renderer.shaderDiskCache`에서도 볼 수 있어요.

## 확인한 범위

- 346: 4 KiB 예산에서 LRU/교체/큰 입력/손상·잘린 파일/전체 키/외부 파일 보존/쓰기 실패/비대기 경합, 네 프로세스 동시 게시와 소유 프로세스 강제 종료 후 복구를 확인했어요. 동시 게시 후 바이트코드는 3,860 B였어요.
- 347: 독립된 실제 D3D 프로세스 두 개에서 래스터·머테리얼·Hi-Z·Bloom·프로브·광원 타일을 실행했어요. 첫 프로세스는 21개 저장, 다음 프로세스는 21개 적중/새 저장 0, 출력 바이트 오차 0이었어요. 안정된 6프레임에서 캐시 통계가 바뀌지 않았어요. 정상 컨테이너에 다른 셰이더 종류를 넣어도 장치 거부 후 원본 컴파일과 다음 적중이 이어졌어요.
- 같은 두 실행의 전체 준비/렌더 관측값은 3,321.03 / 27.90 ms였어요. 부하와 순서를 통제한 성능 실험이나 게임 FPS가 아니에요. 핵심 근거는 다음 프로세스가 해당 21개를 재컴파일하지 않았다는 점이에요.
- 348: 기존 호스트 호환, 한 번의 진단 조회, 기록 없는 프로파일러, 호출자 snapshot 변경 격리, UI escaping, 공용 AI 계약을 확인했어요.
- 350: 실제 패키징한 게임을 격리 프로필로 두 번 실행해 6개 저장 → 6개 적중/새 저장 0과 진단 값 유지, 두 실행의 정상 종료를 확인했어요.
- 351–352: 전체 D3D 게임 검사에서 프로브 강도 변경이 불필요한 재캡처를 일으키는 문제를 찾아 고쳤어요. 공용 캡처 키에서 반사/간접광 강도·혼합 범위·우선순위·박스 투영을 분리했고, 캡처 위치·해상도·근/원거리·반사 횟수·명시 갱신은 계속 무효화해요. 기존 패키지의 두 런타임 파일만 명세와 함께 갱신해 C++/BP·2D/3D·HUD·텍스처·그림자·파티클·변형·Bloom·프로브·장면 전환 전체 검사를 통과했어요. 브라우저 모의 검사도 매번 별개 타깃을 만들도록 고쳐 교체와 최종 제거의 두 해제 및 중복 해제 금지를 확인했어요.
- 전체 게임/설치 검사는 `ENGINE_WORK_349.json`과 후속 `USER_INSTALL_349.json`에서 각각 확인해요. 설치 영수증이 생기기 전까지 설치 확인으로 계산하지 않아요.

## 계속할 렌더링 작업

처음 보는 복잡한 그래프의 최초 컴파일은 여전히 필요해요. 335–344의 GL mixed-frame 실험은 17개 노멀 문맥 및 렌즈/가이드 출력 대조를 통과했지만 기본 경로에 채택하지 않았어요. 현재·미분·이전 노멀을 한 호출 지점으로 합친 상태의 전체 준비/프레임 비용을 확인하고, 투명체의 이전 반사·굴절 분기와 다른 표면 입력 이력을 이어가요. 이 문서는 누적 엔진 목표나 전체 문서/API 분석의 완료를 의미하지 않아요.
