# 문서 실행 취소 기록

열린 문서는 기존처럼 최대40개의 Undo 기록과 Redo 순서를 유지해요. 문서의 일반 JSON 트리를 이전 기록과 비교해 바뀌지 않은 하위 데이터는 같은 저장 공간을 사용해요. 현재 편집 문서와 기록은 분리하고, Undo/Redo로 복원할 때는 다시 복사해요. 따라서 복원한 값을 편집해도 다른 과거 기록을 수정하지 않아요. 파일 묶음 트랜잭션의 표시·충돌·복구 절차는 그대로예요.

이름·경로를 변경할 때는 열린 문서와 Undo/Redo에 들어 있는 참조를 기존 정책대로 함께 갱신해요. 순환·중복 객체 참조, Map/Date/typed array 등 일반 JSON 트리가 아닌 값은 기존 `structuredClone`으로 전체 복사해요. 희소 배열, undefined, NaN/-0, 속성 순서와 데이터 속성인 `__proto__`도 보존해요. 지원하지 않는 함수·Symbol은 기존 복사 오류를 유지해요. 저장 파일의 형식이나 마이그레이션은 추가하지 않아요.

16,384키 문서에서 한 키씩 수정한16기록의 비교는 같은 Node 프로세스에서 명시적 GC 후 측정했어요. 기존 전체 복사는 유지 힙 증가49,018,776바이트·289.06ms, 공유 기록은7,344,992바이트·162.09ms였어요. 유지 힙은 현재 문서도 포함하는 프로세스 관찰이에요. 기기 전체 메모리나 게임FPS 수치로 해석하지 않아요. 별도의65,536키·8기록에서는 기록 객체131,110개·346.34ms였어요.

AI는 `editor.history.inspect`로 열린 문서의 Undo/Redo 개수·고유 객체·중복 참조·추정 데이터 바이트를 조회해요. `objectBudget`은 기본250,000·최대1,000,000이고 예산을 넘으면 `truncated=true`예요. 값 전체와 과거 문서 본문은 반환하지 않아요. `expectedRevision`은 선택적이며 원본·dirty·revision·이력 순서는 바꾸지 않아요. 이 API의 `estimatedPayloadBytes`는 JS 객체 헤더·할당기·현재 문서·파일 묶음 백업을 제외하는 추정치이며, 위의 실제 GC 힙 측정과 달라요.

`node tools/hb.mjs schema --section documentHistory`와 `node tools/hb.mjs context "Undo 메모리" --symbol shareDocumentSnapshot`으로 계약과 소유자를 작게 조회할 수 있어요. 상주 색인·워커·새 타이머·외부 라이브러리는 만들지 않아요.

편집기가 소유한 데이터 속성 이력에는 `ownedPrevious:true`를 주어, 차이가 발견될 때만 결과 객체·배열을 만들어요. 바뀌지 않은 하위 트리를 복사했다가 버리는 할당을 줄이는 방식이에요. 외부 호출의 기본 두 인수 경로는 기존 getter 읽기 횟수를 유지해요. 엔진 내부 옵션을 외부 getter가 있는 이전 값에 적용하지 않아요. `metrics`는 선택적 검사 카운터이며 fallback의 전체 복사·Object.keys 배열·힙 바이트는 세지 않아요.

16,384키·8기록의 같은 순회에서 결과 컨테이너는262,176개에서32,814개로 줄었고, 순회 객체262,176개와 공유 객체229,362개는 같았어요. 변경이 없는 한 기록은32,772객체를 읽고 결과 컨테이너는0개예요. 번갈아 실행한 CPU 관찰4회는 기존79.53~88.05ms, 지연 할당60.28~74.83ms였어요. GC·전체 할당량·게임FPS 측정은 아니에요. 원본·특수값·희소 배열·속성 순서·참조 이름 변경·복원 격리를 별도로 비교했어요.

매번 현재 문서를 비교하는 순회, 변경된 큰 배열의 참조 슬롯, 복원 복사, 씬·블루프린트의 사전 캡처 비용은 남아 있어요. 구조 공유가 모든 문서의 명령 델타나 무제한 Undo를 의미하지 않아요.
