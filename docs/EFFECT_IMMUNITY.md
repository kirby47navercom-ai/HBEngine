# 들어오는 효과 면역

지속/무한 효과에 `immunity`를 지정하면 그 효과가 붙어 있는 동안 새로 들어오는 효과 적용·중첩 갱신을 차단해요. 기존 적용·항목 조건과 같은 `all`·`any`·`none`·`exact` 형식을 사용해요. `effect`는 들어오는 정의의 `grantedTags`, 나머지 `source`·`target`·`instigator`·`causer`는 이번 적용 시점의 태그예요. 역할 사이는 AND이고 기본은 계층 매칭이에요. 순간 효과의 `grantedTags`도 분류에 사용할 수 있지만 차단된 태그를 대상에게 부여하지 않아요. 명시적인 빈 `{}` 면역은 모든 새 효과를 차단해요.

```json
{
  "effect": {"any": ["Status.Poison"]},
  "source": {"none": ["Team.Friend"]}
}
```

사람용 효과 편집기의 **들어오는 효과 면역**과 `effect.immunity.edit({path,expectedRevision,requirements?,clear?,dryRun?,includeData?})`가 같은 검증/Undo/저장 트랜잭션을 사용해요. 지속 시간을 먼저 지정해야 해요. 추가할 때 해당 에셋만 v3로 올리고 제거해도 v3를 유지해요. v1·v2 원본은 자동 변환하지 않아요. 이전 엔진은 v3를 거절해 면역을 무시한 채 실행하지 않아요. 하위 버전으로 명시적으로 돌리려면 면역과 `blocked` Cue를 제거하고 해당 버전의 나머지 조건도 만족해야 해요.

유효한 정의와 적용 인수를 읽은 뒤, 숫자 속성 캡처·연산·라이브 의존 연결·중첩/만료/주기 갱신·들어오는 적용 Cue 전에 판정해요. 차단 결과는 기존 빈 효과 핸들이에요. 면역 효과의 선택적인 v3 Cue `on:"blocked"`는 들어오는 `effect` 에셋·방어 `immunity` 에셋·방어 `handle`·원인 역할의 복사본을 전달해요. `runtime.effect`와 `schema.effectImmunity`로 조건을 조회해요. 기존 BP/C++ ApplyEffect 계열은 같은 공용 실행을 사용해요. 잘못된 정의나 인수의 기본 검증을 면역으로 우회하지 않아요.

기존 효과를 소급 제거하지 않고, 이미 설치한 효과의 레벨·인자 변경도 새 적용으로 취급하지 않아요. 면역의 만료·명시 제거·소유자 퇴역은 기존 수명을 사용해요. 능력 자체의 유효한 활성화 비용은 효과가 차단돼도 소비해요. 여러 효과 처리 중 실제 오류가 나면 비용·효과·Cue를 함께 복원해요. 비동기 능력 로딩 뒤에는 현재 소유자/능력 항목, 쿨다운·활성 상태·태그·비용을 재확인하므로 활성 상태·쿨다운·비용이 바뀐 겹친 요청의 추가 지출을 막아요.

면역은 명시적인 적용 때 대상의 활성 효과를 확인해요. 매 프레임 태그 폴링이나 새 타이머를 만들지 않아요. 지속 태그 조건에 따른 기존 효과의 동적 정지/재개, 네트워크 예측은 별도 잔여예요. 소스·공용 명령 재생 증거와 실제 C++ 바이너리/GUI/설치·실기기 증거를 구분해요.
