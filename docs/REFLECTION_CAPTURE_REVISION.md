# 자동 반사 캡처의 장면 변경 비교

`ReflectionProbe.refreshMode=onChange`는 보이는 메시·광원과 환경의 입력을 비교해요. `once` 모드만 있으면 장면 비교를 수행하지 않고 이전 비교 자료도 해제해요. 숫자 epoch는 이 렌더러 인스턴스 안의 값이며 에셋 ID나 저장할 리비전이 아니에요.

이전에는 장면 전체를 JSON 문자열로 만든 뒤 각 캡처 키에 다시 넣어 이스케이프했어요. 이제 `ReflectionCaptureRevision`이 이전 프레임의 스칼라 사실을 재사용하고, 값이나 구조가 바뀌면 숫자 epoch를 올려요. 해시 충돌에 의존하지 않아요. 본 행렬은 typed array를 직접 읽고 색상도 성분을 읽어요. 같은 프레임에 공유된 재질·기하는 한 번 읽으며 WeakMap은 씬 오브젝트를 강하게 보존하지 않아요. 비교 자료에는 오브젝트 참조를 넣지 않아요.

기존 행렬·인스턴스 버전·모프·본 행렬·광원과 타깃·배경 색·환경·재질 파라미터/표면·텍스처 버전·시간 노드 감지를 유지해요. 라이트맵/강도, 노멀 강도, 물리 재질의 코팅·투과·두께·이방성 등, 추가 텍스처, 기하 UUID·업로드 버전·인덱스·그룹·draw range·모프 속성·렌더 순서와 배경 텍스처도 비교해요. `envMap`이나 재질의 내부 `version`은 캡처 과정 자체가 바꾸므로 비교하지 않아요. CPU에서 정점 배열을 고쳤으면 정상적인 GPU 업로드처럼 `needsUpdate`가 필요해요.

`renderer.hbProbeResources.captureRevision`은 version·retainedScalars·visitedScalars·changed만 알려줘요. 실제 입력값이나 사용자 코드·텍스처 내용은 노출하지 않아요. 수동 모드와 dispose에서 비교 상태를 남기지 않아요. C++/네이티브 캡처 구현과 셰이더 수식은 이번 변경 대상이 아니에요.

검사에서는 기존 입력 246개 변경/무변경 경우와 추가 52개 경우를 대조했어요. 511개 메시·8개 본 배열(각1024 float)의 통제 검사에서 캡처 키208,178B→47B, 본 복사8→0, 색상 배열 복사1,231→0이었어요. 현재24,789개의 스칼라/구조 표식을 보관해요. 실제 GL/PMREM 검사에서 정지 프레임의 재캡처가 없고 광원·기하·라이트맵·노멀·시간 변경이 각각 갱신되며, 라이트맵 강도가 실제 픽셀을 바꿨어요. `once` 전환과 복귀·dispose도 확인해요. 초기 실험의 `type:Time`은 엔진 노드 형식이 아니어서 `key:time`으로 바로잡았고 성공 건수에 실패를 포함하지 않아요.

동일 입력을 순회하는 비용은 남아 있어요. 본의 행렬 갱신과 일반 JSON 메타데이터의 키 열거도 계속해요. 임의의 사용자 셰이더 내부 uniform, 렌더 콜백, 함수가 들어 있는 메타데이터까지 자동 추적하는 기능은 아니에요. 통제된 장면 FPS·힙·다수 HDR 캡처의 총 메모리 개선으로 확대하지 않아요. `tools/check-capture-revision-1611.mjs`와 `tools/check-capture-revision-1612-window.mjs`의 최종 설치 영수증을 함께 확인해요.
