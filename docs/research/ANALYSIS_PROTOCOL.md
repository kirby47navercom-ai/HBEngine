# Unity·Unreal 전체 문서와 API 분석 선행 규약

기준일: 2026-10-04. 이 문서는 **공식 문서의 전체 본문과 API를 먼저 분석하고 검증한 뒤 HBEngine 구현을 진행한다**는 작업 순서를 정해요. 현재는 분석을 시작하기 위한 규약이며, 전체 분석 완료 보고가 아니에요.

이 작업에서는 엔진·편집기·런타임을 수정하거나 실행하지 않아요. 문서 수집, 기존 코드의 읽기 전용 대조, 분석 기록, 분모 확인, 검증만 진행하며 GUI를 실행하지 않아요. 연구 문서와 연구 도구의 커밋·푸시는 기존에 주인님이 부여한 권한과 프로젝트 규칙을 따라요. 기존 연구 문서의 ‘해당 기능을 구현하기 전에 세부 문서를 추가로 확인한다’는 순서는 **두 엔진의 전체 분석 완료 gate를 먼저 통과한다**는 이 규약으로 바뀌어요.

현재 phase는 `research_only`예요. 기준본/공식 root는 [CORPUS_MANIFEST.json](CORPUS_MANIFEST.json), 영속 대기열과 gate 도구는 [reference-ledger.mjs](../../tools/reference-ledger.mjs)를 사용해요. 대용량 목록·원문 snapshot·분석/검증 기계 기록은 Git에서 제외한 `native/build/reference-corpus`에 보존해요. 도구로 확보한 상태와 실제로 읽고 분석한 상태를 분리하고, 도구의 자동 수집이 gate를 열지 못하도록 해요.

## 현재 자료가 입증하는 범위

저장소에서 확인한 아래 수치는 기존 수집 기록이에요. 공식 사이트의 현재 전체 규모를 새로 확인했다는 뜻은 아니에요.

| 기존 자료 | 저장소에서 확인한 내용 | 새 분석에서 인정하는 범위 |
| --- | --- | --- |
| [Unity 목차](../reference-index/unity-manual.json) | 2026-10-02, 3,127항목, `overview` 34개·`indexed` 3,093개 | 제목·URL·부모 관계를 초기 발견 후보로 사용해요. 고유 본문·API·패키지 분모와 달라요. |
| [Unreal 분야 목차](../reference-index/unreal-sections.json) | 2026-10-02, 21개 분야·398개 하위 주제 항목 | 분야별 초기 발견 후보예요. 중복 URL이 있을 수 있고 전체 문서/API 분모가 아니에요. |
| [기존 세부 조사](../reference-index/detail-audit.json) | 2026-10-04 파일 기준 `detail` 48개, URL·읽은 날짜·`readScope`·연결 연구 파일 | 이전에 확인했다고 기록한 부분만 보존해요. 본문 hash·전체 section coverage·API 분모·새 검증 증거 없이 `verified`로 승격하지 않아요. |
| [분야 대조](../REFERENCE_COVERAGE.md), [엔진 분석](../ENGINE_REFERENCE_ANALYSIS.md), 기존 분야별 연구 | 개요·일부 본문·HB 설계 판단·부분 구현을 구분한 기록 | 원출처에서 재확인할 분석 후보예요. 구현 결과가 원출처 전체 분석을 대신하지 않아요. |
| [README](../../README.md), [사람/AI API](../AI_ENGINE_API.md) | 현재 엔진의 기능·API·검사·미구현 설명 | 읽기 전용 비교 대상이에요. HBEngine의 노드/API 수를 Unity·Unreal API 분석 수로 사용하지 않아요. |

기존 원문 캐시인 `native/build/reference-cache`는 provenance/hash를 대조한 뒤 새 corpus에 재사용할 수 있어요. **캐시 파일 존재, HTTP 200, hash 생성, 제목 추출, 자동 요약, 목차 수집은 본문을 읽고 분석한 증거가 아니에요.** 이 규약을 작성하면서 새 공식 본문을 읽었다고 주장하거나 위 기록의 읽기 상태를 올리지 않았어요.

## 전체 분석의 기준본과 분모

‘전체’는 몇 가지 예시 기능이나 현재 구현 분야로 정하지 않아요. 두 엔진의 공식 문서 루트에서 도달하는 매뉴얼·가이드·튜토리얼·참조·API·공식 패키지/플러그인을 열거하고, 그 **버전이 고정된 전체 기준본**을 분석 단위로 삼아요. 웹 문서는 계속 바뀌므로 버전·언어·확인 시점·목차 snapshot을 고정해야 분모와 완료를 검증할 수 있어요. 기준본 고정은 기능 범위를 줄이기 위한 수단이 아니에요.

기준본 manifest에는 다음을 먼저 기록해요.

- 엔진 이름, 실제 공식 버전 표시를 확인한 URL/anchor/hash, 버전 확인 날짜, 제품 문서 루트, 언어, 공식 host, API·패키지/플러그인 루트, sitemap/목차/공식 배포본의 확보 경로를 기록해요.
- 기존 Unity `6000.0`과 Unreal `5.8` 표시는 **기존 조사 기준 후보**예요. 현재 최신 버전이라는 주장 없이 공식 버전 선택기와 본문 표시를 확인하고 기준본을 확정해요. URL에 버전이 없으면 선택된 버전과 응답 본문의 버전 근거도 저장해요.
- 영어 원문을 기본 중복 제거 단위로 사용하되 기존 한국어 요구와 번역의 메뉴/단축키 차이를 연결해요. 한국어 페이지는 원문 대응·번역 누락·버전 차이를 기록해요. 언어 선택으로 원문 기능을 제외하지 않아요.
- Unity 6000.2/6000.5/6000.6, Unreal 4.27 등 기존 기록의 다른 버전은 별도 보조 기준본으로 남겨요. 과거 기능·폐기·변경·대체 동작을 현재 기준본과 대조하고, 과거 문서를 현재 동작의 직접 근거로 사용하지 않아요.
- 모든 역사적 버전·언어를 읽었다고 표현하지 않아요. 확인한 현재 기준본 전체와 확인한 보조 기준본을 각각 보고해요. 새로운 버전에서 추가된 기능은 기준본 변경 요청과 증가한 분모로 기록하고 누적 요구에서 지우지 않아요.
- 공식 패키지/플러그인은 제품의 공식 목록 전체에서 시작해요. 기준 엔진과의 호환 버전, 대체·폐기 상태, 문서 버전, 공식 의존성을 기록해요. 선택적 기능이나 현재 설치되지 않은 패키지도 초기 목록에서 빠뜨리지 않아요. 호환되지 않는 항목도 사유와 대체 경로를 조사해요.

초기 공식 출처 후보는 기존 자료에 있는 [Unity 매뉴얼 목차](https://docs.unity3d.com/6000.0/Documentation/Manual/docdata/toc.js), [Unity 패키지 목록](https://docs.unity3d.com/6000.0/Documentation/Manual/PackagesList.html), [Unity Scripting API 사례](https://docs.unity3d.com/6000.0/Documentation/ScriptReference/Audio.AudioMixer.SetFloat.html), [Unreal 문서 홈](https://dev.epicgames.com/documentation/en-us/unreal-engine/unreal-engine-5-8-documentation), [Unreal C++ API 사례](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Projects/FProjectDescriptor)예요. 이 링크는 발견 시작점이며, 링크를 적었다는 이유로 해당 본문을 이번 작업에서 읽었다고 판정하지 않아요. API 사례 페이지 하나를 전체 API 루트 목록으로 대체하지 않아요.

### 반드시 별도로 확보할 루트

| 엔진 | 누락을 허용하지 않는 문서 계열 |
| --- | --- |
| Unity | 전체 Manual, 전체 Scripting API, 공식 패키지 목록 각각의 버전별 매뉴얼·API, 에디터 API, 공식 도구·서비스와 제품 문서에서 연결한 기능 문서 |
| Unreal | 전체 분야 문서와 하위 문서, 전체 C++ API(모듈·네임스페이스·타입·멤버), 전체 Blueprint API·Node Reference, 전체 Python API, 에디터 API, 공식 플러그인·도구·서비스의 매뉴얼·API |

API·패키지·플러그인 루트는 **분야별 계약을 나중에 만들 때 추가할 항목이 아니라 수집 시작 시점부터의 독립 대기열**이에요. 각 루트의 조회 성공 여부와 하위 목록의 완전성 근거가 필요해요. 공식 문서가 외부 공식 host의 제품 기능으로 연결되면 새 루트 후보로 등록해요. 광고·회사 홈페이지 같은 탐색 링크는 기능 문서와 구분하되 분류 이유를 남겨요. 기능을 포함한 링크를 탐색 링크로 처리해서 제외하지 않아요.

### 수량의 단위

| 단위 | 식별·중복 제거 규칙 | 별도로 보고할 수량 |
| --- | --- | --- |
| 문서 페이지 | `engine + version + locale + canonicalURL`. redirect와 별칭은 canonical 페이지에 연결하고 부모/발견 경로는 모두 남겨요. | 발견·가져오기·본문 확인·분석·검증 완료 페이지, 탐색용 페이지, 미해결 링크 |
| API 타입·멤버 | 선언 언어·모듈/패키지·namespace·owner·member·version. 생성자/소멸자·속성·필드·event·enum·delegate·operator를 포함해요. | API 목록의 전체 멤버 수와 종류별 수 |
| API overload | 완전한 선언 signature와 인수/반환/qualifier. 같은 페이지의 여러 overload를 각각 다뤄요. | 전체 overload 수와 확인·분석·검증 수 |
| 패키지/플러그인 | 공식 ID + 패키지/플러그인 버전 + 기준 엔진 호환성. 내장 항목과 의존성도 목록에 남겨요. | 전체 항목, 버전별 문서·API 분모, 미확보 항목 |
| 본문 구역 | 페이지 hash에 고정된 heading/anchor, 표·예제·경고·이미지 설명·탭별 내용 | 전체 구역과 읽고 분석한 구역 |

목차 항목 수, 고유 URL 수, 페이지 수, API 멤버 수, overload 수는 서로 대체하지 않아요. 매뉴얼 페이지가 전부 확인되어도 API 분모가 없으면 전체 분석 완료율을 계산하지 않아요. 아직 파악하지 못한 분모는 `unknown`으로 표시해요. `0`이나 임의 추정치로 채우지 않아요.

## 상태는 증거를 따라 올라가요

| 상태 | 필요한 증거 | 상태가 보장하지 않는 것 |
| --- | --- | --- |
| `discovered` | 공식 루트/목차/부모 페이지의 발견 경로, URL, 추정 version/kind, 실제 확인 대기 이유 | HTTP 성공, 본문 확보, 읽기, 분석 |
| `fetched` | 성공한 가져오기 기록, 실제 문서인지 검사, canonical/redirect/version, 원문·추출 본문 hash와 위치, 추출 방법 | 본문 읽기와 의미 분석 |
| `body_reviewed` | 같은 hash의 전체 본문을 직접 확인한 기록, 실제 `readScope`, 모든 구역의 읽기 coverage, 표·예제·그림·동적 탭 확인 | 설계 분석·API 계약 검증 |
| `analyzed` | 구역별 사실·제약·예외·제작 흐름, API 단위 분석, HB 적용 판단과 원출처 분리, 관련 누락/모순 처리 | 독립 검증, 전체 corpus 완료 |
| `verified` | 본문 분석 담당자와 별도의 검증자가 원문 hash·구역 coverage·분석 내용·API 목록·관련 링크를 실제 대조한 기록, 검증 실패 없음 | HBEngine 구현 완료나 런타임 검사 통과 |

상태 건너뛰기는 허용하지 않아요. `indexed`는 `discovered` 후보로 옮기고, 기존 `overview/detail`은 `legacyClaims`와 과거 `readScope`로 보존해요. 신규 hash·본문/구역 확인·분석 증거가 준비되기 전에는 과거 상태명을 새 상태에 직접 매핑하지 않아요. 개요 페이지도 자기 본문만 분석하며 하위 페이지 상태를 올리지 않아요.

본문이 바뀌거나 기준 버전·언어·추출 방법이 달라져 hash가 바뀌면 해당 페이지와 이를 근거로 삼은 분석/검증을 stale로 표시해요. 새 snapshot에 대해 다시 확인하고 이전 완료 증거는 이력으로 남겨요. `blocked`, `retry`, `stale`, `broken`, `pending_sections`는 별도의 작업/문제 상태이며 분석 완료 상태가 아니에요.

## 페이지마다 남겨야 하는 증거

자동 수집 기록과 사람이 읽고 분석한 기록을 분리해요. 다음 항목은 필수이며, 해당 사항이 없을 때도 구체적인 이유를 적어요.

| 증거 묶음 | 필수 기록 |
| --- | --- |
| 출처/기준 | stable ID, engine, kind(`manual/guide/tutorial/api/navigation/package/plugin` 등), 요청 URL, canonical URL, redirect 경로, version, locale, package/plugin ID·version, 부모/공식 발견 경로 |
| 확보 | 날짜, HTTP status/content type, 실제 본문 여부, `bodyMethod`(본문 DOM/공식 JSON/PDF 텍스트 등), 원문 위치·`sourceHash`, 추출 본문 위치·`bodyHash`, 추출 도구/버전, 동적 content·표·코드·이미지의 확보 방법 |
| 실제 읽기 | reader와 날짜, `readScope`, 전체 본문인지 부분인지, 실제 읽은 범위가 연결되는 bodyHash, heading/anchor 목록, 구역별 `reviewed/analyzed` 여부·근거 위치, 빠진 표·예제·탭·이미지·링크·다음 페이지 |
| 본문 분석 | 원출처 anchor/구역을 연결한 구체적 사실, 입력/출력/기본값/범위·조건·제약·실패·순서, 제작 흐름·의존성, 예외와 지원 타깃, 불명확한 사항 및 추가 확인 결과 |
| API | 실제 선언 원문·완전한 signature/overload 목록·owner·module/header·언어, parameter/return/output/ref·기본값·제약·호출 가능 단계·thread·ownership·실패/예외·권한·버전·폐기/대체와 관련 API |
| 편집/실행 | 메뉴의 전체 경로, 단축키와 포커스/선택/운영체제 문맥, drag/mouse/Undo·Redo, 문서/에셋의 저장·직렬화·참조·버전 변환, 생성/초기화/실행/일시정지/취소/파괴/정리와 runtime 효과 |
| HB 적용 | C++·Blueprint/노드·사람 편집 UI·AI schema/명령·파일 데이터에서 같은 기능을 제공하는 대응, 기존 코드의 읽기 전용 위치, 차이·설계 판단·누적 요구 ID·향후 검증 조건 |
| 검증 | verifier·날짜, 확인한 sourceHash/bodyHash/분석 record hash, 구역/API coverage 재계산, 사실·추론·HB 결정의 구분, 누락/모순/깨진 링크 목록과 해결 근거 |

hash는 파일에 쓰인 값만 신뢰하지 않고 원문/추출 본문을 다시 계산해 맞춰요. 확인할 원문이 없거나 bodyHash와 읽은 자료가 다르면 검증할 수 없어요. 표/선언/이미지의 의미가 중요한데 텍스트 추출에서 빠졌다면 누락을 기록하고 다른 공식 제공 형태를 확보해요. GUI 실행 없이 확인할 수 없는 내용은 확인 대기 상태로 남겨요.

실질 분석의 근거로 다른 Markdown/JSON 기록을 참조할 때도 `evidenceArtifacts: [{file, sha256}]`로 고정해요. 원장 도구는 명시적인 `docs/research/*.md` 의미 근거를 hash 없이 사용하는 것을 거부하며, JSON artifact의 증거 체인도 다시 검사해요. 참조 문서만 바뀌어도 기존 분석·검증 상태를 그대로 유지하지 않아요. MD의 모든 링크를 자동으로 읽었다고 간주하지 않으며, 이 검사는 읽기·의미 대조를 대신하지 않아요.

### 분석 문장의 기준

제목을 바꿔 쓴 문장, 모든 페이지에 복사한 공통 문장, ‘생성·저장·실행을 지원한다’ 같은 기능명 요약은 실질 분석으로 세지 않아요. 각 판단은 **그 출처의 특정 구역과 그 구역에서 확인한 조건·동작·제약**에 연결되어야 해요. 자동 생성은 발견·본문 추출·분석 초안까지만 할 수 있고, 자동으로 `body_reviewed/analyzed/verified`를 채우지 않아요.

모든 페이지에 편집기나 런타임 의미가 있는 것은 아니에요. 해당 축이 정말 적용되지 않으면 `not_applicable`과 출처를 바탕으로 한 이유를 남겨요. ‘본문에 설명이 없다’는 `not_applicable`과 달라요. 필요한 계약이 본문에 없으면 관련 공식 API/후속 문서를 등록하고 그 요구를 미해결로 남겨요. 탐색용 목차에는 링크·분류·하위 목록 검증을 적용하고 이를 기능/API 본문 분석 수로 세지 않아요.

API 목록은 페이지 제목이 아니라 실제 선언으로 확인해요. C++ 함수의 `const/static/virtual`, 참조/포인터·수명, 비동기 완료, editor-only/runtime, Blueprint exposure·pin 의미, Unity C# API와 native plug-in/IL2CPP 경계가 필요한 경우 각각 남겨요. Unity API를 C++ 선언인 것처럼 바꾸거나 과거 Blueprint Nativization을 현재 기능으로 해석하지 않아요. 공식 자료에 없는 반환값·오류·signature는 만들지 않아요. AI 편집 대응은 원엔진의 공식 기능과 HBEngine에서 정할 설계 판단을 분리해요.

## 수집·본문 분석 순서

1. 기존 URL과 과거 부분 읽기 기록을 가져오고, 새 기준본 manifest의 확인 대기 항목을 등록해요. API/패키지/플러그인 루트도 같은 시점에 등록해요.
2. 각 공식 루트의 전체 목차·sitemap·공식 목록을 확보해요. root별 성공/실패, 페이지네이션, 동적 분류, 검색에만 나타나는 항목, 종류별 분모와 확보 경로를 기록해요. 검색 결과 몇 개나 개요의 첫 화면만으로 목록을 닫지 않아요.
3. 공식 내부 링크와 API의 type/member/overload·부모/파생형·관련 문서 링크를 확장해요. 새 항목이 없어질 때까지 반복하고 루트별 원목록과 비교해 누락을 확인해요. 참고 링크를 읽지 않은 채 부모 본문 완료로 하위 페이지를 완료 처리하지 않아요.
4. 페이지를 가져와 저장하고 canonical/version과 실제 본문을 검사해요. retry/backoff·진행 저장으로 중단 후 이어갈 수 있게 해요. 인증/권한/네트워크/동적 content/공식 오류는 원인과 마지막 시도 날짜를 남겨요.
5. 확보된 실제 본문을 전체 구역별로 확인해요. 긴 페이지는 나누어 읽고 구역 범위를 합산하되 모든 구역을 확인하기 전에는 전체 `body_reviewed`로 올리지 않아요.
6. 구역별 사실·제약과 실제 API 목록을 분석하고 누적 제작 요구에 연결해요. 출처의 사실, 출처에서 추론한 내용, HB 설계, 저장소의 현재 구현 상태를 각각 구분해요.
7. 원문·분모·구역·overload·분석 내용을 별도의 검증자가 대조해요. 같은 담당자의 재확인만으로 `verified`를 부여하지 않아요. 별도 agent가 있다는 사실만으로 독립 검증을 통과하지 않으며, 주 담당자도 분석 agent가 확인한 실제 페이지/분석 보고를 원문과 대조한 경우에만 독립 검증 기록을 남겨요.
8. 전체 gate가 통과할 때까지 발견/분석 대기열을 계속 처리해요. 부분 분야 분석이나 기능 계약 작성이 끝났다는 이유로 엔진 구현으로 넘어가지 않아요.

### 깨진 링크와 문서가 없는 항목

- 404/403/timeout·soft 404·로그인/봇 차단 화면·본문 없는 JavaScript shell은 성공한 문서 가져오기가 아니에요. 실패 URL, HTTP/응답 종류, 실패 이유, retry, 공식 대체본 확인 상태를 남겨요.
- redirect는 목적지 본문과 기준 version을 확인한 뒤 원래 URL의 alias로 연결해요. redirect만 성공했다고 본문 분석을 세지 않아요.
- 공식 폐기/이동 근거가 있으면 기존 기능·현재 적용성·후속 문서/API와 변경 내용을 분석해요. 새 URL의 본문 검증이 끝나야 대응이 완료돼요.
- 공식 API 목록에 있지만 페이지가 없거나 declaration/설명이 빠진 멤버는 API 분모에서 지우지 않아요. 공식 제공 소스·공식 배포 문서 같은 대체 근거의 version/hash를 확보하고 분석할 수 있는지 확인해요. 여전히 계약이 불명확하면 미해결로 남겨 gate를 닫아요.
- 오래된 링크·접근 제한을 임의로 ‘범위 밖’이나 ‘완료’로 바꾸지 않아요. 공식적으로 삭제된 중복/탐색 링크 등의 처리도 근거와 disposition 이력을 남겨 분모 변화가 보이게 해요.

## 전체 분석 완료 gate

분야별 통과와 전체 통과는 별개예요. **아래 조건이 모두 참일 때만 현재 기준본의 전체 분석 완료로 보고하고 엔진 구현을 시작해요.** 검증 도구가 증거 형식을 통과시킨 것과 분석 내용이 원출처에 맞다는 검증도 구분해요.

| 검증 항목 | 통과 조건 |
| --- | --- |
| 기준본 | 두 엔진의 version/locale/공식 root와 package/plugin version이 확인·고정되었고 버전 충돌이 해결됐어요. |
| 루트 확보 | Manual/가이드, Scripting/C++/Blueprint/Python/Node Reference/Editor API, 공식 패키지/플러그인 각각의 실제 전체 목록을 확보했고 분모가 `unknown`이 아니에요. |
| 수집 폐쇄 | 모든 루트의 목차/페이지네이션/동적 목록과 공식 내부 링크 확장이 끝났고 미처리 root·link·신규 발견 항목이 없어요. 각 source의 `discoveryClosed`는 공식 전체 목록의 snapshot/hash·확장 결과·누락 대조 증거가 있어야 `true`가 돼요. 알려진 몇 개의 URL만 비어 있는 대기열은 폐쇄가 아니에요. |
| 본문 | in-scope 모든 문서 페이지의 실제 본문을 확보했고 같은 hash에 전체 구역·표·예제·동적 탭·그림 설명을 확인했어요. title-only/cache-only/partial/stale 항목이 없어요. |
| API 분모 | 전체 타입/멤버/overload를 공식 목록과 대조했고 선언·인수·반환·수명·오류·editor/runtime·언어/노드 노출의 누락이 없어요. 패키지 API도 별도 대조했어요. |
| 실질 분석 | 모든 구역/API에 출처별 구체적 분석과 누적 요구 대응이 있고 제목 요약·공통 template·근거 없는 N/A로 채운 항목이 없어요. |
| 문제 해결 | 미해결 깨진 링크·본문 실패·누락 API·버전 불명·추출 누락·분석 모순·검증 실패가 0이에요. 삭제/대체 처리에는 공식 근거와 현재 대응 분석이 있어요. |
| 검증 | 모든 in-scope 페이지/API가 실제 증거를 바탕으로 `verified`이며 source/body/analysis hash, coverage, verifier 기록이 맞아요. 공식 목록과 ledger 수량을 다시 대조해요. |
| 전체 제작 요구 | Unity·Unreal의 차이/대응/예외와 기존 사용자 누적 요구가 모두 연결되어 있고, 미구현/미지원/대체 설계가 숨겨지지 않았어요. |

`fetched == total`, HTML 파일 개수, 목차 100%, 기존 detail 기록 수, 단일 분야의 verified 100%, HB 테스트 통과는 위 gate를 대신하지 않아요. 단순 검사기가 완료 flag를 읽는 방식도 허용하지 않아요. 실제 원문 hash·구역·API 분모·루트 폐쇄·문제 목록과 대조해서 계산해요.

분모를 확정하기 전에는 각 계열의 발견/확보/검증 수와 미확보 루트를 보고해요. 분모가 확정되면 페이지·API 멤버·overload·패키지별 완료율을 각각 보고해요. **어떤 분모가 알려져 있고 어떤 분모가 아직 없는지**를 항상 함께 표시해요. gate가 닫혀 있으면 남은 일과 이유를 적고 분석을 이어가요. 시간이 오래 걸린다는 이유로 전체 완료를 선언하거나 구현을 시작하지 않아요.

## gate 이후에도 전체 누적 기능을 유지해요

분석이 끝나면 해당 결과로 전체 제작 계약을 확정해요. 2D·2.5D·3D, 쉬운 제작 흐름, 실제 C++/노드 공통 실행, 머테리얼/애니메이션/블루프린트 편집, 실제 에셋 가져오기, 사람/AI 공용 편집과 주인님이 추가한 세부 요구를 모두 유지해요. 주인님이 든 예시는 다른 기능을 제외하는 목록이 아니에요.

누적 요구에는 다음 분야와 새로 발견한 모든 기능을 계속 추가해요: 프로젝트/설치/업데이트·편집기/도킹/단축키·에셋/임포트/참조/복구·객체/컴포넌트/Prefab/장면·2D/물리/충돌·입력·C++/Blueprint/자료형/직렬화/수명·렌더링/재질/조명/VFX·애니메이션/시네마틱·게임 UI/접근성/지역화·오디오·AI/내비게이션·Terrain/큰 월드/LOD/스트리밍·네트워크/복제/권한·XR·프로파일/디버그/자동화·패키지/플러그인/에디터 확장·플랫폼/빌드/cook/배포/저장·공식 문서에서 새로 발견한 도구/서비스예요. 이 나열 자체가 완전한 분모라는 뜻은 아니에요.

가벼움·단순한 조작은 전체 기능을 유지하면서 설계하는 기준이에요. 필요한 세부 계약을 삭제하거나 몇 가지 기능만 MVP로 바꿔 완료 처리하는 근거가 아니에요. 구현 순서는 의존성/공통 기반/검증 가능성으로 정하되 다음 작업으로 미룬 항목도 전체 요구·완료 분모에 남겨요. 특정 기능을 HB에서 다른 방식으로 제공한다면 사용자 결과·데이터·수명·오류·C++/노드/AI 동등성을 분석 근거와 함께 명시해요.

분석 `verified`는 구현 `complete`와 달라요. gate 이후 구현한 기능은 **사람의 실제 조작 → 공통 모델/타입 검증 → 디스크 저장/재열기 → C++/노드와 실제 runtime 효과 → AI 공용 명령 → 오류 복구와 재현 검사**로 따로 검증해요. 전체 엔진 제작 완료는 남은 누적 기능이 없을 때만 판정해요.

## 다음 담당자가 이어갈 때

manifest/ledger, 원문 캐시 위치·hash, 공식 root 확보 상태, 페이지/API/overload/package별 분모, 상태별 수, 마지막 처리 항목, 미해결 link/API/section, 기존 부분 읽기 이력, gate 실패 사유를 인계해요. 읽지 않은 항목은 읽지 않았다고 그대로 기록해요. 새로운 담당자도 제목 수집을 본문 분석으로 바꾸거나 부분 분석을 전체 완료로 보고하지 않아요.

현재 이 규약의 완료 상태는 **규약 작성 완료, 전체 공식 본문/API 분석은 진행 전 또는 진행 중**이에요. 실제 ledger의 증거와 전체 gate 결과가 나오기 전에는 이를 전체 분석 완료로 변경하지 않아요.
