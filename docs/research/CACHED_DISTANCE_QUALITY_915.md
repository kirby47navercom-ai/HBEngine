# 기존 거리장의 품질 교체와 준비 지연 조사 (910–919)

880–904의 예산 적합화에 이어, 이웃 제거·표시 변경으로 공간이 생기면 기존 낮은 해상도 필드도 다시 구워요. 현재 필드를 유지하며 새 필드를 준비하고 완료 후 한 번에 교체해요. 기존 필드와 새 예약을 둘 다 로컬 페이로드 예산에 넣으므로, 같은 예산에서 새로 여는 장면보다 최종 격자가 작을 수 있어요.

- 필드가 없는 기하와 보류 재시도가 선택적 품질 향상보다 우선이에요. 소유자마다 품질 향상 작업은 동시에 하나예요. 오브젝트 수 제한은 추가하지 않아요.
- 최소 향상 폭은 12.5% 또는 2격자 중 큰 쪽이며 요청 최대에 도달하는 마지막 작은 단계도 허용해요. 다시 검사하려면 이전 검사보다 여유 용량이 10% 이상 늘어야 해요.
- 얇은 기하의 바이트를 큐브 비율로 추정하지 않고 실제 레이아웃으로 결정해요. 63→64의 작은 마지막 단계도 가능해요.
- 공유 계약의 `upgradingFields`, 소유자 생성 후 누적 `qualityUpgrades`, 최대 3개의 `upgradeFailureExamples`로 같은 상태를 읽어요. 실패·취소 시 현재 필드를 유지하며 제거·해제는 해당 소유자 작업만 취소해요.
- 원래 기하의 상대 bounds 9개 숫자를 워커의 기존 분석 결과에서 전달해요. 메인 스레드의 BVH·bounds 재계산, 추가 전체 기하 순회, GPU 타깃·읽기·영속 캐시를 추가하지 않아요.

`distance-upgrades-912-ALuwAg`의 실제 워커·장면 증거:

1. 큰 이웃 제거 후 기존 15/8 격자를 55/15로 순차 교체해요.
2. 작업 중 이전 데이터와 준비된 오브젝트를 유지하고, 강체 이동 5회에 볼륨 재복사 0이며 모든 상태에서 기존 필드+예약이 예산 이하여요.
3. 새 기하가 기존 작은 필드의 선택적 향상보다 먼저 준비돼요.
4. 정적 40프레임에 새 작업이 없고, 용량 히스테리시스·작업 중 해제·입력 해제·idle 워커 0을 확인해요.

`cached-quality-regressions-913.json`: 실제 원본 삼각형 베이크의 bounds 전달·얇은 격자 예산·작은 최종 단계·CPU 거리/atlas/엄격 API 회귀 4개와 문법 5개. 기존 `distance-resolution-881-OaQXDW`의 예산·보류·재시도 및 `distance-field-editor-822-n2jUML`의 사람 편집·Undo/Redo·AI CAS·저장을 유지해요. 최신 실제 패키지·설치본 C++ 표시 변경→캐시 교체→AO 화면·블루프린트 대조는 `ENGINE_WORK_916.json`, `USER_INSTALL_918.json`에 기록해요.

이중 상주 공간이 부족하면 품질 향상을 보류해요. 카메라 클립맵·이동 LOD·시간 신뢰도·bent normal·지형/변형체·투명 기하를 구현한 증거는 아니에요.

`trilinear-preparation-911-V0K9So`에서는 큰 UV·노멀 텍스처·금속 반사 그래프를 GL ABBA로 비교했어요. 1..2회 밉 루프를 명시적인 첫 샘플+조건부 둘째 샘플로 펼친 후보는 평균 3839.25→4160.95ms로 약 8.4% 느렸어요. 렌즈·이동 이력 가이드 준비가 지배적이었어요. 이 후보는 엔진에 적용하거나 구현 성과로 계산하지 않아요. 첫 910 시험은 테스트 정규식 오류로 실행되지 않아 성능 증거에서 제외해요.

캐시·부하를 완전히 통제한 cold-start나 전체 Complex141 증거는 아니에요. 초기 컴파일 지연과 합성 FXC 역순 호출 문제는 잔여 목록에 유지하며 캐시 품질 개선과 섞어 해결됐다고 표시하지 않아요.
