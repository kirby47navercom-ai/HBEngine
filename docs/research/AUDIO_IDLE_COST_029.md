# 오디오 유휴 처리·좌표 예약 후속 분석

2026-10-06. [028](AUDIO_ANALYSER_LIFETIME_028.md)의 버퍼 재사용에 이어, 재생이 끝난 측정 노드의 처리와 변하지 않은 공간 좌표의 예약 비용을 줄였어요. 부분 소스 분석·제품 검사를 전체 문서/API 분석이나 8시간 안정성으로 계산하지 않아요.

## 실제 읽은 원문

[Chromium audio_param_timeline.cc](https://chromium.googlesource.com/chromium/src/+/751b533743c567cc069f12da53e4470f51008e7a/third_party/blink/renderer/modules/webaudio/audio_param_timeline.cc)의 고정 커밋은 `751b533743c567cc069f12da53e4470f51008e7a`, 원문 SHA-256은 `ee5ccb366b8b7c46f54265b1da96c5399892b79e7c0b2ac3317b0d936c16612c`예요. 이번 직접 읽기는 449–709, 949–1003, 2019–2054줄이에요. 전체 파일·호출자·렌더링 알고리즘 전체 읽기와 독립 검증은 아니에요. 원문·범위·응답 기록은 `native/build/frame-order-docs-20261006/audio-param-followup-capture.json`에 있어요.

- 449–460: `SetValueAtTime`은 주 스레드에서 음수가 아닌 시간을 검사하고, 잠금을 잡아 새 SetValue 이벤트를 `InsertEvent`에 보내요. 같은 값이라는 이유로 여기서 예약을 생략하지 않아요.
- 462–560: 선형·지수 램프와 Target/Curve는 별도 이벤트예요. Target의 시간 상수가 0이면 SetValue, Curve는 길이 2 이상·양수 기간을 요구하며 끝값 이벤트도 추가해요. 이 부분을 단순 좌표 설정과 같은 호출로 취급하지 않아요.
- 562–701: 정렬 위치를 구하고 Curve의 겹침을 검사한 다음 이벤트 목록과 새 이벤트 집합에 넣어요. 실제 자동화의 순서·겹침 규칙을 보존해야 해요.
- 949–974: 현재 시각 조회는 잠금 확보 실패·이벤트 없음·첫 이벤트 전이면 기본값을 반환해요. 976–1003은 프레임 범위 계산 시작과 클램프까지 읽었으며 나머지 계산은 이번 읽기 범위 밖이에요.
- 2028–2051: 취소 이벤트 제거는 새 이벤트 집합도 정리하고, 오래된 이벤트 제거는 최소 한 이벤트를 남겨요. 따라서 이 코드만으로 자동화 이벤트가 영구 누적된다고 결론내리지 않아요.

진단 창의 실제 `Browser.getVersion`은 `Edg/154.0.4258.53`, revision `5af6e80f702cffe10645c6d6433668f011b739be`예요. 해당 revision으로 공식 저장소의 `realtime_analyser.h`를 조회한 결과는 404예요. 위 고정 Chromium 소스가 설치 WebView2와 일치한다는 증거가 없으며 주소의 심볼 해석·FFT/배열/지연 정리 소스·WebKit 구현은 계속 미해결이에요.

## HBEngine 적용

공용 `AudioRouting`에서 이전 소리를 지우는 동안에만 측정 노드에 무음을 흘려요. 오디오 시계가 `fftSize + 128` 샘플을 지난 뒤 노드를 연결 해제하고, 활성 소리와 정리 중인 노드가 모두 없으면 측정 타이머도 멈춰요. 컨텍스트가 일시 정지됐으면 정리 시간이 지난 것으로 간주하지 않아요. 보관 한도는 기존 16개를 유지하며 종료 시 모두 정리해요.

청취자·공간 음원의 마지막 좌표를 복사해 두고, 변경된 축만 `setValueAtTime`으로 예약해요. 원본 좌표 배열을 제자리에서 바꿔도 다음 업데이트에 반영해요. 믹서 스냅샷·페이드·실제 이동은 계속 업데이트하며 일반 AudioParam 자동화의 의미를 바꾸지 않아요. 이는 불필요한 호출 감소이고 메모리 증가의 단독 원인 규명은 아니에요.

## 실행 증거와 한계

- `check-buffered-audio.mjs`, `check-audio-sources.mjs`, `check-ui-audio.mjs` 통과. 반복 200회 재사용, 이전 버퍼가 남은 경우 분리, 유휴 16개 한도, 종료·늦은 디코딩 정리, 정지 좌표 200회에서 3축 초기 예약만 수행, 변경한 축 즉시 반영을 확인했어요.
- 실제 Windows `features-window-PVSo1Z/acceptance.json`: 강한/약한 40ms PCM 12개 모두 신호 오차 0.005 이내, 측정 노드 생성 1개, 유휴 연결 해제·타이머 종료 통과. 전체 기능과 1,000발·적 30·C++ 600프레임은 59.404176fps, 작업 p95 11ms, 오류 0, 기존 PC gate 통과예요. 정확한 60.000fps 보장이나 실제 Android 중급 기기 검증으로 바꾸지 않아요.
- 직전 코드 `a3ad7ec`의 원격 iOS `37433705272`: 실제 device/simulator SDK 컴파일, 별도 iPhone SE 3 시뮬레이터 실행, 12개 신호·생성 1개·배경 정지·복귀 통과. 후속 유휴 타이머·좌표 변경의 동일 소스 iOS 검사는 별도로 진행해요. 실물·서명·청취는 false예요.
- 자연 GC 진단 `memory-controlled-XAZtAi`: 같은 GameInstance·중립 입력·동일 RPC 경로에서 123.716초 청취 좌표 예약 포함(총 private 588.75→663.203MiB), 124.056초 예약만 생략(666.203→662.5MiB), 123.658초 게임 일시 정지(672.695→576.141MiB)예요. 두 활성 구간 요청은 각각 36,568/36,618회, 샘플링된 524,284바이트 할당은 각 단계 1개예요. 강제 GC는 없고 서로 다른 초기 상태·자연 GC·샘플링 영향이 있어 단독 누수 원인이나 장기 안정성을 입증하지 않아요.
- 고정 이전 D3 패키지의 실제 8시간 검사 `kiosk-soak-zjUtGE`는 계속 진행해요. 약 6,738초·112회 리셋·실행 오류 0에서 전체 private 2,076.56MiB로 증가했어요. 이 기록은 새 소스의 검사도, 안정성 통과도 아니에요. 원래 시계·검사 기준·실패 기록을 유지해요.

Android 후속 APK와 같은 최종 소스 iOS 결과·설치 해시는 후속 진행 기록에 추가해요. 이 문서의 주소 추가는 발견 대기열 등록이며 기존 전체 corpus/API gate를 승격하지 않아요.
