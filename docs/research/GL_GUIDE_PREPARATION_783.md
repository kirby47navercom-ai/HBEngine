# 775–783 · GL 생성 코드와 가이드 준비 비용

## 구현

`ray-program-operands.js`는 엔진이 생성한 명령 블록에서 읽지 않는 value/meta/a–d 및 X/Y 별칭 선언을 제외한다. 산술식·연산 순서·레지스터·패킹·필드/차분 마스크는 바꾸지 않는다. 첫 load 구역 표식은 생성 코드 진단/기존 실험과의 호환성을 위해 유지한다. 원본 셰이더 텍스트나 사용자 코드를 받아 정리하는 도구가 아니다. 계산이 끝난 결과의 최적화가 아니라, 드라이버 앞단에 불필요한 선언을 덜 전달하는 처리다.

`compileRayMaterial`/장면 prewarm/실제 packed `rayInfo.guideSpecular`는 기존 가이드와 같은 조건을 보수적으로 계산한다. 기본 금속성>.5와 거칠기<.4, 또는 코팅>.5와 코팅 거칠기<.05의 가능성을 본다. 그 채널을 동적으로 쓰는 IR이면 가능한 값으로 간주한다. 관련 없는 채널만 동적일 때는 불필요한 거울 가능성을 추가하지 않는다. 상수 파라미터/C++ 수정은 기존 소스·머테리얼 키에 따라 다시 평가한다. 메타데이터가 없는 예전 패킷은 일반 경로를 유지한다.

GL 가이드는 세 경로를 사용한다.

- `general`: 거울 가이드가 가능하거나 정보가 없다.
- `noMirror`: 거울 가이드는 불가능하지만 투과 가능성이 남아 있다. 굴절/매질 처리를 유지한다.
- `diffuse`: 거울과 투과가 모두 불가능하다. 확산 표면의 무조건 반환 이후 이차 경로 꼬리만 생성 소스에서 제외한다.

현재/이전 노멀, 이전 머테리얼 입력·클록·밉, 가시성·표면 변경 거부, 렌즈 제어는 확산 반환 이전에 그대로 남는다. `curved` 검증은 무광에서도 필요하므로 끄지 않는다. 반사·굴절 모델을 단순화하거나 현재/이전 값을 공유하지 않는다. 가이드 전용 상태 변경은 가이드와 그 이력을 재준비하되 기존 경로 추적 머테리얼·컴파일 프로그램은 유지한다. `pipelinePreparation.guideMode` 및 `schema.pipelinePreparation.glGuideSpecialization`에서 선택을 확인할 수 있다. 새 설정 버튼·GPU 버퍼/타깃/상시 readback/캐시는 추가하지 않는다. 기존 가이드 타깃은 상태 변경 때 보수적으로 해제/재생성한다.

이 특화는 GL용이다. 공통/native 셰이더 본문과 `RayPrograms.hpp`/`ScreenEffects.hpp` 생성 결과, 네이티브 컴파일 소유자와 Player769 SHA는 유지한다. WebGPU 알고리즘도 대조 대상으로 유지한다.

## 784–785 · 첫 부분 업로드에서 빠진 기하 데이터

실제 패키징 게임의 검은 화면은 디노이저 이전 원시 경로부터 발생했다. CPU atlas는 정상인데 GPU의 첫 BVH 행·삼각형이 모두0이었다. 로컬 Three r180 `WebGLTextures.js`의 `uploadTexture`/`updateTexture`는 새 저장소를 할당할 때도 DataTexture의 updateRanges가 있으면 해당 구간만 채운다. 셰이더 준비를 기다리는 동안 CPU의 Time 머테리얼이 뒤쪽 행만 변경해 첫 업로드에 그 행만 남은 것이 원인이다.

`gl-ray-atlas.js`는 엔진 소유 Float32 광선 atlas를 실제 GL 사용 직전에 한 번 전체 초기화한다. 리소스·Source·크기·샘플러가 바뀌거나 컨텍스트가 복구되면 다시 전체 초기화하고, 같은 리소스의 정상 후속 프레임은 Three의 기존 행 부분 전송을 유지한다. 새 텍스처/FBO/readback/디스크 캐시는 만들지 않으며 안정 프레임마다 stamp 배열을 만들지 않는다. `renderer.rayAtlasRecovery`와 불변 `schema.pipelinePreparation.glRayAtlas`로 AI도 초기화 횟수·CPU 페이로드 바이트와 범위를 읽을 수 있다.

7858wUp5p는 실제 GeometryGIWorld와 Time 그래프로 첫 전송 전 뒤 행만 변경했다. 수정 없는 대조군은 첫 행0을 재현했고, 보정 후 전체 Float32 GPU 데이터가 CPU와 일치했다. 이후 행 부분 갱신·dispose·샘플러 변경·실제 컨텍스트 상실/복구·두 번째 renderer도 통과했다. GPU 읽기용 FBO는 검사에만 존재한다. 이 수정은 초기화/복구의 정확성 문제이며 전체 렌더링 성능이나 상시 전체 업로드를 뜻하지 않는다.

남은 일은 반사·굴절이 많은 복잡한 GL 준비, FXC/장치/필터 비용, 전역 광학 대응·복합 거친 매질의 정밀 확장, 디스크 mip IO/전체 GPU heap/정확한 보조 뷰 수요와 누적 엔진 목표다. 현재 표본으로 cold-start·장시간 RAM·전체 성능·전체 분석 완료를 주장하지 않는다.
