# 486–496 네이티브 준비 대기 분리

Microsoft의 [멀티스레딩 개요](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro)는 장치와 단일 컨텍스트의 소유 규칙을 구분하고 DXGI/Present도 같은 컨텍스트 소유 스레드에 유지하도록 설명해요. [D3DCompile](https://learn.microsoft.com/en-us/windows/win32/api/d3dcompiler/nf-d3dcompiler-d3dcompile)은 HLSL을 바이트코드로 바꾸며 D3DCompile2로 바꾸는 것 자체에 성능 이점은 없다고 설명해요. 읽은 범위와 원문 지문은 CORPUS_MANIFEST.supplemental496에 등록해요. 전체 공식 본문/API gate는 올리지 않아요.

소스에서 공용 캐시 잠금과 화면 캐시 잠금이 전체 FXC 및 장치 콜백을 감싸는 것을 확인했어요. 잠금 범위를 캐시 조회/게시로 줄이고 설정 세대가 달라진 이전 작업의 새 루트 저장을 막았어요. 워커는 장치/컨텍스트·가변 프레임 상태를 캡처하지 않아요. 결과 채택과 실제 필요한 단계 전체의 준비 판정은 렌더 소유 스레드에서 해요. 이전 키·실패·취소 및 큐 제한을 분리하며 이미 준비된 변형은 진행 중인 다른 FXC를 기다리지 않고 복원해요.

489의 이전 소스 대조에서는 장치 콜백을 제어한 동안 조회가 차단됐고 현재 소스는 조회/설정 변경이 진행됐어요. 큐 중복1·취소1·성공3·실패1·유휴0/재시작2를 검증했어요. 기존347의 실제 D3D21저장→21적중·0재저장·6프레임IO불변·잘못된 셰이더 단계 캐시 복구도 보존했어요. 490은 준비 중 캡처·세대 교체·취소·컴파일/연결 실패와 AI/사람 진단을 검사해요. 실제141 게임은22프레임/23Present와 준비 중 샘플0·C++4.21ms·끄기62.65ms·최종 변형664채널/이력/해제를 통과했어요.

총 FXC 비용이 사라진 것은 아니에요. 시간 가이드3535ms 관찰은 기존3516ms와 동일한 통제 조건이 아니므로 속도 개선으로 계산하지 않아요. 여전히 남은 전체 항목은 ENGINE_STATUS와 ENGINE_WORK496에 유지해요.
