# 일반 표면 준비·소유·실행 기록

## 근거와 구현 선택

[Microsoft D3D11 멀티스레딩](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro)의 장치/컨텍스트·DXGI 구분31–50행과 [D3DCompile](https://learn.microsoft.com/en-us/windows/win32/api/d3dcompiler/nf-d3dcompiler-d3dcompile)의 서명·매개변수·반환·요구사항32–131행을 재독했어요. 기존 supplemental496 원문을 재사용하고 전체 연결 API·드라이버 문서를 읽었다는 뜻으로 세지 않아요.

`SceneRenderer::createProgram`이 FXC와 디스크 접근 중에도 `gpu.mutex`를 잡는 경로를 확인했어요. 소스 생성을 공통 함수로 옮겨 동기 SDK의 결과와 키를 유지하고, 잠금은 GPU 생성·파라미터 갱신 구역에만 둬요. 새 `SceneProgramPreparation`은 기존 화면 효과 큐를 공유해 본체와 그림자 바이트코드만 만들어요. 큐를 얻을 때 기존 컴파일 캐시/라이브러리를 먼저 초기화해 종료 시 워커 join보다 먼저 파기되지 않게 해요.

작업이 `Program`·렌더러·장치를 캡처하지 않아요. 결과 채택은 소유 스레드에서 하고, 임시 COM 셰이더를 성공한 경우에만 게시해요. 실패 바이트코드는 새 컴파일 경로로 한 번 재시도하고 반복 실패는 반환해요. 생성한 두 셰이더가 모두 준비된 뒤에만 해당 draw를 실행해요. queued 핸들을 파기하면 기존 큐의 수집이 취소하고, 이미 컴파일 중인 결과도 파기한 프로그램으로 돌아갈 포인터가 없어요.

브리지는 준비 중 ID만 보관해 유휴 프레임에서 전체 머테리얼을 다시 순회하지 않아요. 기존 asyncShaderPreparation을 사용하는 일반 실행기는 자동으로 새 경로에 연결돼요. 집계된 본체·그림자 단계만 보고해 객체별 거대한 상태 목록을 매 프레임 전송하지 않아요. 소스·완성 바이트코드는 채택 뒤 보관하지 않고 기존 한정 캐시를 사용해요. 대기 큐 예산은 대기 작업의 비용이며 전체 장면·텍스처 메모리 상한이라는 뜻이 아니에요.

프레임 시작 때 준비 여부를 한 번 판단해 Present 중 워커가 끝난 것을 이미 그린 이력으로 승인하지 않아요. 준비 중에는 종속 화면 효과·그림자·반사·하늘 캡처를 게시하지 않아요. JS의 기존 그림자/반사 캐시는 마지막 pending 뒤 프레임에서 다시 갱신하도록 연결해요. 캡처 중 상태가 끝나는 경합도 시작 상태를 보존하고 준비 후 다시 그려 해결해요.

## 검사 구분

553은 실제 D3D SDK에서 큐를 의도적으로 멈춰 ordinary draw의 유지·pending draw 제외·파라미터·move·동기 픽셀 일치·취소·컴파일 오류·한 번 재시도·유휴 종료를 검사해요. 첫 결과의 `singleWorker` 필드는 동시 개수가 아니라 기존 `workersStarted`의 이름을 잘못 붙인 것이어서, 소스에서 `workerStarts`로 바로잡았어요. 숫자2를 동시에 워커 두 개라고 해석하지 않아요. GetTickCount64의 제출 시간0은 그 시계의 분해능보다 짧은 관찰이지 실제 처리 비용0이나 FPS 보장이 아니에요.

555는 집계 진행·오류/취소·AI 계약·캡처 경합을 검사하고 기존490 상태 검사를 유지해요. 556은 외부 창을 건드리지 않는 소유 hidden Win32 창에서 실제 브리지의 upload/Present/상태-only 채택/reset을 검사해요. 초기에 테스트의 C++ auto 혼합 선언과 HWND 없는 Present를 고쳤으며 엔진이 사용자 창을 여는 방식으로 우회하지 않았어요.

새 플레이어를 포함한 일반 2D/3D 실행기·그림자/프로브·C++ 제작과 복잡한 준비·복구·캡처 및 가져오기 합성 게임은 별도 통합 근거로 남겨요. 이 문서 자체는 그 검사 통과를 대신하지 않아요. 최종 결과·소스 지문·설치 확인은 ENGINE_WORK560에 기록해요. 전체 초기 GL/FXC 비용·자원 생성·혼합 노멀과 누적 엔진 잔여 목표는 별도로 유지해요.

558 전체 실행은 프로브 진입 전의 스프라이트·3D·그림자·머테리얼·텍스처 검사를 진행한 뒤 새 프로브의 미준비 바인딩으로 실패했어요. 새로 지연한 프로브가 아직 필터링되지 않았을 때 일반 객체로 전달한 것이 원인이어서, 브리지가 준비된 프로브만 바인딩하도록 고쳤어요. 전체 통과로 다시 쓰지 않고, 같은 소유 프로젝트와 C++ 캐시를 재사용한559에서 프로브와 남은2D·해제 검사를 완료했어요. 첫559의 해제용 Three 장면 누락은 검사 프로필 수정이에요.

프레임 판단 뒤 마지막 pending 프로그램을 제거하는 경우도 해당 프레임의 이력 승인을 막도록 고쳤고556에 별도 회귀를 추가했어요. 최종562 플레이어의 실제496/548 게임도 통과했어요. 347은 서로 다른 프로세스의21개 캐시 저장→21개 적중·출력 오차0과 장치 거부 복구를 유지했어요. 이 수치로 처음 전체 준비 시간이나 FPS 개선을 주장하지 않아요.
