# 전역 반사 후보·GPU 아틀라스

2026-10-21. RND-03의 큰 메시/인스턴스 후보 제한을 실제 실행 경로에서 줄이는 작업이에요. 최종 소유 SHA·검사·설치는 ENGINE_WORK_1131.json과 후속 영수증에 확정해요.

## 근거와 범위

[Unity URP 본문](https://docs.unity.com/en-us/engine/6000.6/manual/lighting-overview/lighting/reflection-probes/introduction)의235–278줄을 다시 읽었어요. CPU의 오브젝트 경계 후보, 픽셀별 영향·하늘 잔여, 간접 드로와 Forward+/Deferred+의 차이를 대조했어요. HB의 아틀라스 구조 자체가 Unity의 내부 구현과 같다는 주장은 아니에요.

[Epic Reflection Captures](https://dev.epicgames.com/documentation/en-us/unreal-engine/reflections-captures-in-unreal-engine)의 모양/영향·작은 캡처 우선 구역을 다시 확인했어요. 구형 캡처와 작은 캡처의 우선 점유는 현재 박스·정규화 정책의 별도 잔여로 남겨요.

[Khronos OpenGL4.3 명세](https://registry.khronos.org/OpenGL/specs/gl/glspec43.core.pdf)의8.13·8.13.1, PDF235–236쪽에 나온 면 선택·이웃 면·세 면 모서리 필터를 읽었어요. 모서리의 세 표본 평균은 권장 방식이고 구현 재량이 있음을 구분해요. DirectX에서 모든 드라이버가 비트 단위로 같다고 가정하지 않고 실제 TextureCube 출력과 대조해요. 총744쪽 중 지정 구역 밖 본문·연결 문서/API를 분석 완료로 계산하지 않아요. supplemental1130/read-scope.json에 지정 구역만 남겨요.

## 연결한 구현

브라우저는 서로 다른 CubeUV 맵을 장치 크기 안에서 포장하고, DirectX는 면·밉을 원래 해상도로 복사해요. 픽셀은 전체 순위에서 자신을 포함하는 첫 두 프로브를 고르고 기존 affine fade·정규화·원래 환경 잔여를 사용해요. 인스턴스도 각 픽셀의 월드 위치를 사용해요. 작은 드로의 직접 두 맵 경로는 유지하고 큰 경계가 세 후보 이상에 걸칠 때만 추가 자원을 만들어요.

DirectX의 초기 수동 모서리 재구성은 머테리얼 로브마다 코드가 크게 펼쳐졌어요. 동일 머테리얼 시험에서 수동 샘플 후보는9.69초, GPU 패딩 뒤4.45초, 표면 후보 선택을 한 번 준비한 뒤4.24초가 관찰됐어요. 마지막 두 수치의 작은 차이는 개선 입증으로 세지 않아요. 통제된 ABBA나 전체 로딩/FPS 측정이 아니며 기존 GL Complex141의 약8/7초 문제와 구분해요. 현재는 캡처 변경 때 컴퓨트로 가장자리를 만들고 화면에서는 하드웨어 필터를 사용해요.

캡처 identity/revision·형상·메타데이터 변경을 구분해요. 정지 상태와 밝기 변경에서는 맵 복사/패딩을 하지 않아요. 네이티브 전송도 승인된 마지막 후보 자료와 같으면 생략하고, 수신 목록/스크래치와 GPU 메타데이터를 재사용해요. 삭제·재설정·소유자 교체·해상도 변화에서는 각 소유 자원을 정리해요. 장치 크기 한도는 검사하되 임의의 오브젝트 개수 상한은 추가하지 않아요.

WebGPU의 WebGL 폴백에서는 설치된 Three의 RT 복사 함수가 비영점 목적지의 끝 좌표에 width/height를 그대로 넣는 것을 확인했어요. DataTexture 상수 시험만으로는 나타나지 않았고 실제 그라데이션 PMREM 타깃에서 차이가 났어요. 해당 경로의 소유 FBO와 상태를 확인한 뒤 올바른 끝 좌표로 복사하는 작은 어댑터를 추가했어요. 의존 패키지는 수정하지 않았어요.

## 증거와 실패 구분

1116-JVtP0F: 이질 사각형 배치/독립 비중첩·장치 오류/10003개의 작은 사각형·100정지 업데이트/소유자·메타데이터·해제. 실제10003프로브 GPU 성능을 뜻하지 않아요.

1117-9n0axL: GL/GPU/강제 WebGL 폴백에서4영역/4인스턴스·해상도·밝기/정지 전송/해제·복원, 각각54개의 금속/코팅 그라데이션 RT 조건을 표준 머테리얼과 비교해요. 방향 시험의 최대 차이는5.97e-8 이하였어요.

1119-lV3LzO: 실제 D3D의 기존 캡처/SH/GGX/코팅/IOR/두 후보 회귀와4영역/4인스턴스/메타데이터/갱신/해상도/해제,21방향·거칠기×4픽셀의 TextureCube 대조를 통과했어요. 최대 차이는1이며 허용2를 유지했어요. 최종1119-RMzcPS에서 패딩의 정지 재사용도 통과했고 표면 프로그램 컴파일4371ms를 기록했어요.

1120-NNkxNw: 새 실행기로 패키징한 실제 C++/BP 네 영역에서 빨강·초록·파랑·노랑을 확인했어요. 네 번째 프로브의 C++ 밝기 변경과 BP 복원은 캡처4·면/밉 복사150·패딩25를 유지하고 후보 전송1→2→3만 바꿨어요. 최종fixture는 발광.4/ambient0/realtimefalse를 사용해요. 실제게임 GL1120-tShlaw, GPU1120-JuyK49, D3D1120-PpduDz에서 네 영역·C++밝기/BP복원과 정지캡처/복사를 통과했어요. 설치 증거는1131에 연결해요.

초기 C++ friend/경고, BP position 핀에 value를 사용한 것, 바닥 피벗 큐브를 중앙 피벗으로 배치한 것, legacy 환경에서 skyEnabled=false여도 남는 주변광, SkyLight에 지원하지 않는 captureResolution16을 준 것은 구현/검사 수정 기록으로 구분해요. 실제 캡처색만 비교하도록 검사용 프로젝트에 밝기0의 환경 액터를 사용했으며 오류를 숨기려고 픽셀 오차를 늘리지 않았어요. GL1120-kw4qmL의 HDR4 빨강→주황은 Three ACES 입력/출력 행렬의 색역 압축이었어요. 실제 로컬 tonemapping_pars_fragment를 대조하고 영역 구별 fixture 발광을.4로 낮췄으며 판정값은 바꾸지 않았어요. HDR 정확도는 선형float 타깃1117/1119에서 그대로 비교해요. 준비 타임아웃 당시 컴파일은 실패가 아닌 진행 상태였어요. 검사 도구는 준비 큐가 살아 있으면 같은 창에서 기다리도록 바꿨어요.

## 남은 범위

공간 타일·클러스터 가속과 큰 장면 성능/메모리, 픽셀 우선 점유·구형 캡처·lightmap 혼합, 임의 셰이더 변위/인스턴스별 모프의 경계는 남아요. 소스 대조에서 native raster의 eye−position 시선과 ambient diffuse의 금속 처리도 별도 품질 대상으로 확인했어요. 현재 게임 검사는 카메라 중앙과 주변광0을 사용하므로 직교 off-axis·주변광의 백엔드 일치를 증명하지 않아요. 전체 엔진·전체 문서/API 완료를 주장하지 않아요.
