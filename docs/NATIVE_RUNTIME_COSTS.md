# 네이티브 공용 런타임 비용 · 2026-11-02

프레임 제한이나 게임 에셋을 바꾸지 않고 엔진 공용 렌더링·UI 경로를 수정했어요.

- 네이티브 렌더러의 장면·그림자·2D 보조 패스는 숨긴 부모 아래를 순회하지 않아요. 숨김/표시/이동/루트 숨김/복원과 2D 보조 패스의 전체 전송 명령을 기존 경로와 대조했어요.
- UI는 보이는 요소가 실제로 그릴 그림·글꼴만 준비해요. 숨긴 메뉴의 그림은 읽지 않고, 표시하는 첫 프레임에는 준비를 기다려요. 다른 보이는 위젯과 공유하는 그림은 유지하며, 쓰지 않는 그림은 해제해요.
- 소수 배율에서 SVG를 선택하면 대응 PNG까지 함께 읽지 않아요. 크기 변경으로 선택이 바뀌면 필요한 그림을 준비하고 이전 그림을 해제해요.
- 큰 정적 UI 그림의 반복 축소는 캔버스마다 최대 8MiB·32개 결과를 재사용해요. 한 그림의 여러 표시 크기를 함께 보관해 크기 교대로 인한 재생성을 막아요. 애니메이션·가변 이미지·반투명·회전·소수 이동·그림자 등은 기존 그리기를 사용해요.
- 글자·폭·글꼴·자간 등이 같으면 줄바꿈과 글꼴 측정을 재사용해요. 결과는 최대 128개·문자 32768개 단위로 제한하며 글꼴 등록과 UI 해제 때 비워요.

`--report`를 사용하는 네이티브 엔진 프로필은 프레임별 `ui`와 최종 `ui.timing`에 `assetsMS`, `paintMS`, `encodeMS`, `submitMS`, `totalMS`를 기록해요. `submitMS`는 UI 요청의 응답 대기 시간이에요. UI와 장면 렌더링이 겹쳐 실행되므로 이 값을 `renderAndHUDMs`에 다시 더하면 안 돼요. 일반 실행에서는 이 시간 측정을 하지 않아요. `ui.images`, `ui.sourceImagePixels`는 소스 그림 수와 픽셀 수이며 RSS나 VRAM 사용량이 아니에요.

검사는 생성한 그림·위젯과 소유 캔버스로 실행했어요. 이미지 36조건·글자 96조건의 픽셀이 같았고, 공용 `WidgetSystem`의 시작 직후 한글 변경·표시 전환·스냅샷·해제도 연결했어요. `ENGINE_WORK_3410.json`에 명령·소스 해시·근거를 기록했어요.

이 PC의 교차 CPU 비교에서 그림 그리기 0.589→0.205ms, 글자 처리 0.375→0.197ms, 숨긴 자식 5000개를 가진 장면의 전송 명령 구성 1.276→0.812ms였어요. 실제 게임 전체 FPS와 GPU 시간은 이 검사로 측정하지 않았어요.

UI 전체 경로의 시간은 전송 방식의 영향을 크게 받아요. 다른 작업의 무손실 RGBA/Zstd 전송이 있는 작업 트리에서는 1.747→1.206ms였지만, 그 변경을 제외한 기존 PNG 전송 경로에서는 13.291→12.696ms였어요. 서로 다른 두 전송 방식의 수치를 이번 캐시 개선으로 합산하지 않아요. 이번 커밋은 다른 채팅이 수정 중인 전송 형식·C++·스크롤·대용량 업로드 변경을 포함하지 않아요. 설치본과 실제 게임의 최종 성능 판정도 별도예요.

재현 명령은 `node tools/check-native-widget-assets.mjs`, `node tools/check-native-widget-image-cache.mjs`, `node tools/check-native-widget-text-cache.mjs`, `node tools/check-native-widget-runtime-flow.mjs`, `node tools/check-native-widget-frame-cost.mjs`, `node tools/check-native-visible-traversal.mjs`예요. 공용 런타임의 기본 UI와 네이티브 빌더가 이 소유 모듈을 함께 사용해요. 별도 게임 수정은 필요하지 않아요.

## WORK3412 · 공용 전송과 배포 리소스

WORK3410에서 제외했던 검증된 전송·C++ 상태 경로를 별도 소유 후보로 통합했어요. 미검증 spans·zero-alpha·frame RPC 후보와 다른 DPI 변경은 제외했어요. 위젯 descriptor는 참조로 비교하고 C++ UI setter는 바뀐 leaf만 복원해요. UI 인코딩은 premultiplied RGBA를 무손실로 보존하며, ACK가 온 프레임만 XOR 기준이 돼요. 실패/창 크기 변경은 full로 복구하고 UI 해제 때 기록을 비워요. nativeDecodeMS·nativePresentMS는 submitMS에 포함된 수신 측 구간이므로 중복 합산하지 않아요.

동일 1280×720 HUD의 교차 순서 50프레임(별도 warmup10)에서 그리기+인코딩 p50은43.6876→4.0705ms, p95는45.9267→6.9968ms, p99는48.0315→8.0613ms예요. ACK를 즉시 돌려준 CPU 비교이므로 OS 표시·전체 게임 FPS 수치가 아니에요. warmup 포함60번 전송 문자열은14,567,060→224,404바이트였어요. XOR 기록은720p에서픽셀+scratch 약7.03MiB를 사용하고, 축소·해제 시 큰 이전 버퍼를 반환해요. 이 비용 절감을 전체 RSS 감소로 표현하지 않아요.

별도로 실제 Win32/DX11 release 패키지40프레임·공용 C++·묶음 SVG/한글 글꼴/음성·OS 입력·정상종료를 검증했어요. 게임 원본은 사용하지 않았어요. 배포 리소스는 [리소스 묶음](GAME_RESOURCE_ARCHIVE.md), 소스/근거 해시는 ENGINE_WORK_3412.json에 있어요.

## WORK3414 · 변경 사각형과 C++ 읽기

UI의 최종 픽셀이 같으면 전송을 생략하고, 작은 변경은 그 사각형만 무손실로 보내요. 입력·레이아웃 계산은 유지해요. 변경 영역이 넓으면 full/XOR 경로를 유지하며 ACK되지 않은 프레임은 기준으로 사용하지 않아요. C++는 캔버스/사각형 범위와 프레임 순서를 검증하고 투명 지우기까지 원래 픽셀을 보존해요. 35개 실제 JS→C++ decoder 사례와 매 프레임 한글을 바꾸는 Win32/DX11 release40frame에서 확인했어요.

동일720p HUD CPU 비교의 p50 3.9043→3.2652ms, p95 7.5092→4.5279ms, p99 7.5864→4.8748ms예요. 즉시 ACK를 사용하는 그리기/인코딩 검사이므로 게임 FPS 수치가 아니에요. 해당 사례의 scratch는3,686,400→704바이트예요. 실제640×360 실행의 마지막 HUD 사각형은1872바이트였고, 전체 화면은921600바이트였어요.

C++ Input getter는 keys/pointer JSON을 복사하지 않아요. UI GetText/GetValue/GetListItems는 읽기만으로 객체를 dirty로 표시하지 않아요. 임의 mutable bridgeWidget 접근은 계속 복원돼요. 256키 상태에서 공개 getter 묶음2000회의 C++ 내부 중앙값35.4179→5.6355ms를 확인했어요. 전송·물리·렌더 시간을 포함한 전체 프레임 측정과 구분해요.

## WORK3418 · 게임플레이 조회와 상태 복원

C++ 블랙보드·AI·상태·애니메이션/IK/모프·오디오·시퀀스·내비게이션·파티클·능력·환경 질의의 읽기는 이제 객체를 수정한 것으로 표시하지 않아요. 읽기만 했는데 다음 호출에서 전체 객체 JSON을 비교하던 비용을 제거했어요. 명시적인 가변 접근과 setter는 계속 dirty로 표시하고 다음 호출에서 권위 상태로 복원해요. 반환값 캐시가 없으므로 setter 직후 getter도 바로 반영돼요. 없는 선택 상태의 기본값·누락/모호한 이름 오류를 유지해요.

실제 release C++ worker에서 공개 조회78종·기본값32종·누락/범위 오류10종·모호한 검색4종·수정 직후 읽기와 다음 RPC 복원을 대조했어요. 같은 PC에서 이전/수정판을 번갈아4회 측정한500객체의 조회+다음 호출 복원 구간은 중앙값2.6762→0.6286ms, p95 3.6875→0.7585ms, p99 7.1393→0.8778ms예요(각512표본, 묶음별16회 준비 제외). 읽기만 한 객체의 불필요한 복원 표시는500→0이에요.

이 수치는 해당 엔진 구간이며 물리·그리기·IPC·게임 전체 FPS를 포함하지 않아요. 이전의40프레임 실행 확인은 기능 smoke 검사였고 성능 합격 근거가 아니에요. 이번에는 같은 smoke/렌더러 검사를 반복하지 않았어요. 결과·fixture는 native/build/gameplay-read-cost-WquiSP/acceptance.json와 같은 폴더에 있어요. 변경SDK는 C++를 다시 빌드하거나 게임을 재패키징하면 적용돼요.


## UI 전송·생성/삭제·시작 자원 · WORK3420

네이티브 UI는 한 개의 Skia 작업 스레드와 승인된 한 프레임만 유지해요. 무손실 premultiplied RGBA의 바뀐 64px 타일들을 로컬 binary pipe로 보내며, PID·범위·순서·종료·오류를 확인해요. 화면이 같으면 보내지 않고 크기 변경은 full로 복구해요. 기존 PNG/Zstd 경로와 목록의 기존 처리는 유지해요. UI decode/present는 submit 안의 시간이며 중복 합산하지 않아요. 실제 16프레임의 한글·SVG·1.5배·회전·투명·스크롤·입력 사각형 픽셀을 대조했어요.

C++ 동기화에서 좌표만 바뀌면 그룹 변환만 맞추고 머테리얼 검사를 반복하지 않아요. 불변 UI의 이전 버전은 보존하며, 객체 값이 바뀌어도 모양 검증을 통과한 비교 코드를 재사용해요. 키·배열 길이·형식이 달라지면 다시 검사하고 가변 변경·C++ 쓰기 뒤 복원도 유지해요.

기존 ActorPool 획득/반환은 이미 있었어요. 풀 대기 객체의 첫 시각 준비를 미루고 획득 이벤트 전에 완료해요. 반환은 자원을 재사용하며, 실제 삭제는 presentation.remove를 통해 GPU/CPU 자원을 해제해요. 모델 포즈·머테리얼·UV·기하 상태는 인스턴스별이고 원본 읽기/이미지 픽셀은 공유해요. 숨긴 glTF 모델은 포즈/기하를 유지하되 이미지 디코딩을 미루고, 표시할 때 원본 픽셀 준비를 기다려요. 마지막 소유자 삭제는 공유 모델/아틀라스도 해제해요. 전역 객체 수 제한을 추가하지 않았어요.

Windows 하드웨어 장치 생성 실패는 WARP를 시도하고 양쪽 오류를 남겨요. 오디오 출력 장치가 없으면 무음으로 실행하고 진단을 남겨요. 실제 WARP 계산·4 PE import closure를 확인했지만 다른 물리 PC·수신 백신·물리 장치 교체 검증과는 구분해요. D3D12 네이티브 백엔드는 이 변경에 없어요.

최종 소유 숨김 창, 동일 게임/원본 저장·120 요청, 일반 실행 frameDone 간격을 재판 52.54→100.66 FPS로 측정했어요. Auric 동일 위치는 114.35→116.08 FPS이며 두 표본만으로 작은 차이를 확정 개선율로 부르지 않아요. 120 목표는 미합격이에요. 움직임 비교의 sparse heartbeat 때문에 입력 유지 시간이 달랐던 후보, 첫 초기 회귀와 실패한 포장 실험은 최종 성능 근거에서 제외해요. 계측 실행의 FPS는 일반 실행 FPS로 쓰지 않아요. 상세 정본은 [ENGINE_WORK_3420.json](research/ENGINE_WORK_3420.json)이에요.

## 삭제 자원 GC 회수 확인 · WORK3422

설치 `59c56a17eb91063a`의 실제 모델·아틀라스·지연 이미지 소유 모듈로 격리 Node 검사를 실행했어요. 네 장면 묶음에서 128개 인스턴스와 16개 원본을 만들고, 풀에 둔 동안 픽셀을 유지한 뒤 실제 해제했어요. 캐시 자체는 살려 둔 채 304개 WeakRef의 객체·텍스처·픽셀 배열이 전부 회수됐고, 각 묶음 끝 ArrayBuffer는 41,719byte였어요. 자원 dispose 16회와 내부 source/instance/lease 0도 확인했어요.

`--expose-gc`와 명시 GC는 검사 자식 프로세스에만 사용해요. 게임 프레임의 강제 GC는 추가하지 않았어요. 이 근거는 JavaScript 소유 그래프의 회수 가능성을 확인하며, C++ 힙·GPU 드라이버·모든 게임의 장시간 누수·GC 중단 시간까지 합격시킨 근거는 아니에요. 도구: `tools/check-native-resource-gc.mjs`, 결과: `native/build/resource-gc-Bo0aUA/acceptance.json`. 제품 소스 변경이 없어 설치를 다시 만들지 않아요.
