# 태그별 게임플레이 Cue 자산

콘텐츠 브라우저에서 **게임플레이 Cue** 자산을 만들고 소유 오브젝트의 Ability System → 게임플레이 Cue에 지정해요. 능력/효과의 기존 Cue 태그·발생 시점을 자산 경로와 대응시켜 별도 이벤트 그래프 없이 음향과 파티클 burst를 실행해요. 기존 사용자 Cue 이벤트도 계속 전달해요.

각 경로에는 고유 ID, 태그, 정확 비교, 발생 시점, play/stop, 채널, 음향, 음량/피치, 공간 음향, 파티클 방출 수를 지정해요. 태그는 기본적으로 계층을 비교하며 모든 일치 경로를 작성 순서대로 실행해요. 음향은 기존 오디오 자산/로컬 미디어를 한 번 재생해요. 파티클은 소유 오브젝트의 기존 활성 ParticleSystem을 사용해요. play의 빈 음향·0개 파티클은 작성 중 비워 둘 수 있는 no-op이에요.

음향 채널은 소유자 세대·Cue 자산·효과 핸들/능력 자산·채널로 구분해요. 같은 채널을 다시 재생하면 해당 음성만 교체하고 stop은 해당 음성/대기 요청만 취소해요. 예를 들어 resume 시 play, inhibit/remove 시 같은 채널 stop 경로를 만들 수 있어요. 여러 효과 인스턴스와 다른 오브젝트의 소리를 함께 멈추지 않아요. 파일의 loop 설정은 Cue one-shot에 상속하지 않아요.

Cue 경로는 초기화 시 한 번 읽어 검증·컴파일하고 같은 자산의 동시 요청을 공유해요. 유휴 타이머나 매 Cue의 자산 재읽기를 추가하지 않아요. 효과/태그/비용 트랜잭션이 확정된 후 실행하므로 거절한 효과는 음향/VFX를 만들지 않아요. 억제·재개 등 실제 전이만 사용하고 주기 catch-up의 묶음 Cue는 한 번만 표현해 과거 효과음을 몰아서 만들지 않아요.

오브젝트 교체·풀 비활성·VM 종료/세대 변경을 비동기 오디오/파티클 준비 전후에 확인해요. 늦게 생성된 소유 파티클은 폐기하며 대기 음향이 같은 ID의 새 오브젝트에 붙지 않아요. 경로 실행 실패는 기존 로그와 `gameplayDebug.cues`의 마지막 요약에 기록하고 확정한 게임 수치와 사용자 Cue 이벤트를 유지해요. 상태/에러 배열을 무한히 쌓지 않아요.

AI는 일반 `gameplaycue` 자산 생성·`document.patch`/CAS/dryRun/Undo/save와 기존 컴포넌트 편집을 사용해요. 공용 BP/C++ ApplyEffect/ActivateAbility 명령이 같은 런타임으로 이어져요. 기존 참조 분석·이름 변경·4대상 콘텐츠 수집이 `cueAsset`/`sound`를 따라가요. 스키마는 `gameplayCue`에서 조회해요.

별도 VFX 템플릿 생성/부착, 여러 ParticleSystem 중 선택·지속 VFX 정지 핸들, 네트워크 Cue 예측/복제는 별도 잔여예요. 이 구현의 소유 headless 검사와 실제 창의 영상·OS 음향 출력 검증은 구분해요.

Cue 자산은 AbilitySystem 초기화 때 읽고 실행 도중에도 기존 BP/C++ 컴포넌트 문자열 설정의 `AbilitySystem.cueAsset`로 교체/비울 수 있어요. 새 경로의 파일을 새로 읽어 검증한 뒤 속성과 경로를 함께 반영하고, 같은 경로는 파일 I/O 없이 유지해요. 최근 요청만 반영하며 실패/소유자 교체/컴포넌트 제거·비활성/외부 바인딩 변경이면 이전 설정을 보존해요. 준비 중 다른 속성의 수정은 유지하고, 이전 프로그램의 음성·대기 오디오와 늦은 파티클 burst를 취소해요. 이미 살아 있는 burst 입자는 일반 emitter 수명을 따르며 다른 VFX까지 지우지 않아요. 비활성 컴포넌트의 경로 설정은 다음 초기화를 위한 속성만 바꿔요. 검사: `node tools/check-gameplay-cues-2528.mjs`에서 실제 공용 VM/native-command replay·사람 폼·저장/이름변경·4대상 콘텐츠 수집을 확인해요.

2536 이후 재바인딩 검사는 같은 소유자가 살아 있는 상태의 deferred 음향/팩토리 취소, 중첩 요청·실패·수정 재시도·무변경 I/O·다른 속성 보존과 기존 native component 명령 재생을 포함해요.
