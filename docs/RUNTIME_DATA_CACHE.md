# 런타임 JSON 읽기와 캐시

게임이 읽을 수 있는 서로 다른 JSON 파일의 개수에는 고정 제한을 두지 않아요. dataJsonRead/dataTableRead는 캐시가 가득 차도 다음 파일을 읽고, 오래 안 쓴 항목부터 퇴출해요. 퇴출한 파일을 다시 요청하면 원래 에셋 공급자에서 읽어요. 단순히256을1000 같은 더 큰 게임 제한으로 바꾸지 않아요.

기존 결함은 createPersistentQueries의 Map이256개에 도달하면 "실행 데이터 에셋256개 제한" 오류를 내고 계속 거부한 것이에요. 처음 도입된26bd257c 이후 그대로 남아 있었어요. 외부 엔진/JSON 형식의 필수 제한이 아니에요. 별도의 cacheAssetReader는 이미 퇴출을 지원했지만, 이 경로는 사용하지 않았어요.

공용 retainedAssetReader가 Promise 중복 읽기, LRU 순서, 실패 재시도, clear 이후 늦은 완료 방지와 예산을 소유해요. 일반 에셋 독자는 반환값을 복사하고, 데이터 질의는 최초에 검증·복사·정규화한 전용 스냅샷을 사용해요. 데이터 질의는 문자열만 돌려주므로 매번 전체 테이블을 복제하지 않아요. inspect의 entries/bytes는 보관 캐시 항목 수와 JSON 문자 기준의 대략적인 payload 비용이에요. 프로세스 전체 RAM 측정값이 아니에요.

기본 캐시는 최대256개/추정 payload32MiB를 보관해요. 이 수치는 메모리에 남길 양이며, 누적해서 읽을 수 있는 파일 수가 아니에요. 파일별 JSON 형식/깊이/크기 검사, 허용 경로, 저장 슬롯 검사는 그대로 유지해요. 사용자가 읽기를 요청하지 않은 파일을 미리 로드하지 않아요.

공용 제작 흐름: engine-services의 컴포넌트/노드 실행, game-storage의 네이티브 질의, run-project의 실행 세션, mobile-player의 웹/모바일 cooked HTTP 질의가 모두 같은 createPersistentQueries를 사용해요. 공개 C++/노드 시그니처는 바뀌지 않아요. 캐시 clear는 기존 실행/세션 수명을 따라요.

수정 근거: tools/check-runtime-data-cache.mjs 및 ENGINE_WORK_3440.json. 이전판257번째 실패, 새판5000개 JSON+표 읽기,512개씩의공용 서비스/네이티브 어댑터/웹·모바일 HTTP 경로, 예산 퇴출·재읽기·동시성·복사 격리·오류 재시도·종료 수명·저장 호환을 묶어 검사해요. SDK 바이너리와 실제 휴대폰을 새로 검증했다는 뜻은 아니에요. 기존 게임 패키지는 갱신한 엔진으로 다시 빌드해야 해요.
