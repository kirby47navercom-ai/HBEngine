# 이전·현재 머테리얼의 WebGPU 텍스처 공유

WebGPU의 현재/이전 프레임 머테리얼 컴파일러는 같은 atlas load 함수와 같은 uniform 객체일 때 기존 텍스처 Map과 `gpuFn`을 함께 사용해요. 다른 바인딩은 공유 전에 거부해요. UV·삼각형·법선·시각·밉 계산은 각 프레임 문맥을 유지하고 텍스처 표본 함수만 재사용해요.

새 전역 캐시·GPU 버퍼·이력 이미지·유니폼·자동 GPU 읽기는 없어요. 이전 컴파일러마다 있던 Map을 하나로 연결하고, 실제 셰이더 빌더별 함수 수명은 기존 `gpuFn`의 WeakMap을 유지해요. DirectX 바이너리와 GL 기본 경로, 머테리얼 IR/필드 마스크·파일 버전은 바꾸지 않았어요.

실제 WebGPU 검사에서 현재·이전 노멀을 한 셰이더에 넣은 17포즈의 공유/비공유 오차는 0이었어요. 두 문맥은 단위 법선으로 관측되고 서로 다른 결과도 포함해요. 텍스처를 쓰는 표본의 WGSL Texture/TextureLevel 함수는 4개에서 2개가 됐어요. 2D·배열·3D·큐브와 12필터, 384좌표/LOD/legacy 표본도 변경 전 컴파일러와 오차 0이었어요. 예를 들어 월드 위치 UV 표본은 86,295자에서 72,064자로 줄었어요.

실제 C++/블루프린트 WebGPU 게임의 첫 path/시간 가이드 전환은 3654/2454ms였어요. 이는 한 번의 부하 미통제 전환 표본으로 FPS나 속도 개선율이 아니에요. 초기 준비 지연 목표는 계속 남아 있어요.

## GL 실험과 다음 작업

`ray-program-context-sharing.js`는 생성된 current/prior 프로그램에서 기하 입력과 공통 연산 본문을 분리하는 실험 도구예요. GL 기본 경로에는 적용하지 않았어요. `--shared-inputs`의 17포즈 GL/GPU 대조는 통과했고 프로그램 문자열도 줄었지만, 전체 준비 ABBA 2024/1957/2026/1931ms에서 속도 개선 근거는 얻지 못했어요. 이 실험을 성능 최적화 완료로 세지 않아요.

다음 후보는 가이드의 현재·미분·이전 노멀 표본을 한 호출 지점에서 평가하도록 공통 연산에 프레임 문맥을 전달하는 방식이에요. 드라이버가 공통 함수를 여러 호출 지점에 다시 펼치는 비용을 확인하고, 이전 기하·법선·UV·밉의 독립성과 동작 분기 거부를 보존해야 해요. 이 문서 작성 시점에는 그 후속 혼합 문맥 가이드를 구현한 상태가 아니에요.

`npm run test:ray-sampler-sharing`으로 재현해요. 테스트만 GPU를 읽으며 프로덕션 프레임 조회는 추가하지 않아요. 자세한 SHA/범위는 ENGINE_WORK_334/USER_INSTALL_334에 기록해요.
