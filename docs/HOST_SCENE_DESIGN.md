# C++ 호스트 장면 전환 설계 (2026-11-14)

## 목표

- 1만 개 1000FPS, 10만 개 240FPS 이상.
- 변하지 않은 오브젝트에는 프레임 작업이 없어야 해요(JS도 C++도 오브젝트마다 도는 일이 없어야 해요).
- AI가 다루는 쪽(게임 로직, 편집기, 블루프린트 연결)은 JS에 그대로 둬요. 매 프레임 많은 오브젝트를 도는 핵심만 C++로 내려요.

## 현재 구조와 한계

- C++: 창, D3D11·D3D12 그리기, 셰이더, 그리기 기록 보관(`SceneRenderBridgeCore`).
- JS(내장 V8): 장면 트리(three.js), 행렬 갱신, 화면 밖 판정, 묶음, 정렬, 그리기 목록(`order`), 그림자 캐스터 목록, 프로브 캡처 목록.
- 그래서 오브젝트가 많으면 JS가 매 프레임 전부를 한 번씩 건드려요. 오브젝트 하나에 아무리 짧게 걸려도 1만 개면 수 ms가 나와요.

## 단계

### 1단계: 호스트 정적 집합(컬링·인스턴스 그리기)

- **JS**
  - 깨끗한 정적 그룹 가운데 묶음 후보인 메시(불투명, 같은 상태 키)를 정적 집합으로 올려요. 같은 상태 키와 렌더 순서·그림자 여부가 집합 키예요.
  - 집합은 구성원 행(월드·노멀·색·UV)과 경계 구를 바이너리로 한 번 보내요.
  - 올린 그룹은 이후 순회에서 속성 하나로 건너뛰어요. 그리기 목록에는 집합 ID 하나만 들어가요.
- **승격과 강등**
  - 그룹이 정적으로 깨끗한 상태가 일정 프레임 이어지면 올려요.
  - 강등 조건: 오브젝트 변경 알림(리비전 구독), 표시·행렬 갱신 표시·부모 변경, 장면에서 빠짐(순회 중 못 봄), 검증 모드·정적 끄기, 반사 프로브 존재(1단계 제외).
  - 강등된 그룹은 다음 프레임부터 원래 경로로 그려요.
- **C++(브리지 공용, D3D11·D3D12 모두)**
  - `cullSet` 자원: 행과 경계 구를 보관하고, 전체 행 인스턴스 버퍼(`#all`)를 만들어요.
  - 매 프레임 메인 패스: 뷰·투영 절두체로 경계 구를 판정해요. 보이는 행만 모은 인스턴스 버퍼(`#view`)로 인스턴스 그리기를 한 번 해요. 보이는 목록이 같으면 다시 올리지 않아요.
  - 그림자 패스는 `#all`을 그려요(절두체 밖은 래스터에서 잘려요).
- **같아야 하는 것:** 화면 픽셀(메인·그림자). 불투명 집합은 렌더 순서 구역 맨 앞에 그려요(깊이 판정이라 결과 같음).

### 2단계: 반사 프로브·2D 정렬

- 프로브 캡처 목록에 집합을 넣어요(프로브 영향 범위 판정을 호스트에서).
- 2D는 정렬 결과가 보이므로, 정렬 키가 변하지 않은 구간을 호스트에 두고 바뀐 항목만 다시 정렬해요.

### 3단계: 변환·물리 호스트화

- 움직이는 오브젝트의 변환을 호스트 배열에 두고, JS는 바뀐 것만 써요(행렬 갱신·전송 비용 제거).
- 물리를 네이티브(C++) 물리 엔진으로 옮겨 WASM 경계 비용을 없애요.

## 검증

- 1단계: 정적 집합 켜기·끄기의 D3D12 화면 픽셀 비교(그림자 포함), 강등 시나리오(이동, 숨김, 머테리얼 변경, 제거), 리비전 검증 게임 5종.
- 측정: 3D 1만·10만 개(프로브 없는 장면 포함), 2D 1만 개.

## 진행 (2026-11-14)

### 1단계 구현

- **C++ 브리지**(`native/desktop/SceneRenderBridge.hpp`, D3D11·D3D12 공용)
  - `cullSet` 자원: 행(인스턴스 176바이트)과 경계 구를 바이트로 받아 보관해요. 전체 행 버퍼 `#all`, 보이는 행 버퍼 `#view`를 만들어요.
  - 그리기의 `cullSet`: 메인 패스 전에 뷰·투영 절두체로 구를 판정해요. 보이는 목록이 바뀔 때만 `#view`를 다시 올려요. 보이는 행이 없으면 그리지 않아요.
  - 그림자·프로브 패스는 `#all`로 그려요.
  - 통계: `cullSets`, `cullUploads`, `cullVisible`. 해제는 `release.cullSets`.
- **JS**(`prototype/native-scene-renderer.js`)
  - 승격 대상: 깨끗한 정적 그룹 가운데 모든 그리기가 불투명 묶음 후보이고 2D 노드가 없는 그룹. 같은 리비전으로 30번 인코딩된 뒤 대기열에 들어가요.
  - 대기열 적용: 256개 이상 모이거나 가장 오래된 항목이 60번 지나면 적용해요. 이번 인코딩에 방문한 그룹만 옮기고, 그 그리기는 이번 프레임 목록에서 빼요(이중 그리기 방지).
  - 집합 키: 묶음 상태 키 + 렌더 순서 + 그림자 여부. 집합이 바뀌면 행·구를 바이트로 한 번 보내요.
  - 순회는 소유 그룹을 속성 하나로 건너뛰어요. 강등 조건: 변경 알림(구독), 표시·행렬 갱신 표시·부모·부모 단위행렬 변화, 순회 중 못 봄, 반사 프로브, 검증 모드, 정적·묶음·호스트 끄기(`renderer.hbHostStatic=false`, 실행기 `HB_HOST_STATIC=0`).
  - 그림자 수신 판정: 수신 구성원이 있는 집합이 있으면 수신자가 있다고 봐요.
  - 반사 프로브 수집은 호스트 소유 그룹의 하위 트리를 걷지 않아요. 2D 준비는 표시 색 개수를 쓰지 않는 네이티브 렌더러(`hbDisplayCounts:false`)에서 호스트 소유 그룹을 건너뛰어요.
- **검사**
  - `check-host-static-sets`(신규): 켜기·끄기 170프레임. 컬링한 메인 패스가 매 프레임 같아요. 그림자 캐스터는 상위 집합이고, 늘어난 행은 그림자 절두체 밖에만 있어요. 이동·숨김·머테리얼 변경·제거·카메라 이동을 포함하고, 그룹 198개를 옮겨요. 변경 알림 처리를 끄는 변이(100프레임)와 표시 검사를 끄는 변이(110프레임)를 잡아요.
  - `check-native-mesh-batch-gpu host`(신규 모드): 실제 D3D12 150프레임 화면이 켜기·끄기에서 픽셀 차이 0이에요(태양·점광 그림자 포함, 집합 5개, 보이는 행 272개).
- **측정**(3D 1만 개, 반사 프로브 없는 장면, 400프레임, 교대 2회): 끄기 98.7·111.4ms → 켜기 43.2·55.3ms.
- **남은 큰 비용**(켜기 프로파일)
  - 게임 서비스 틱의 오브젝트 전체 순회 8회(컴포넌트 조회, 오브젝트마다 await)
  - 장면 행렬 갱신 호출(프레임당 여러 번, 그룹마다)
  - 화면 밖 칸 구성원 검증(오브젝트마다)
  - 물리 단계
- 다음: 컴포넌트 색인으로 서비스 순회 제거, 화면 밖 그룹도 호스트로 승격, 반사 프로브 장면 지원(2단계).

### 컴포넌트 색인 (2026-11-14)

- `prototype/component-index.js`: 컴포넌트 종류별 오브젝트 목록을 목록 순서대로 들고 있어요. 목록 변경(감시한 변경 함수, `listVersion`)과 컴포넌트 변경 알림으로 갱신해요. 64번에 한 번은 처음부터 다시 세어 비교해요. 다르면 보고하고 색인을 꺼요(이후 매번 다시 세요).
- 게임 서비스 틱의 전체 순회 7개를 대상만 돌게 바꿨어요.
  - 대상: 오디오 리스너, 카메라 흔들림·스프라이트 번쩍임(쓰기 지점에서 등록), 파티클, 애니메이션 예산·런타임 LOD(샘플한 오브젝트 추적), 애니메이션 그래프·믹서·애니메이션, 몽타주(`montageObjectIds`), 모프 디버그, 월드 충돌 LOD, 2D IK
  - 64프레임마다 한 번은 원래대로 전체를 돌아, 알리지 않은 경우도 맞춰져요.
  - 몽타주 적용은 원래 오브젝트마다 `await`가 걸렸어요(1만 개면 프레임당 마이크로태스크 1만 개).
- 검사 `check-component-index`(신규): 무작위 400단계(컴포넌트 추가·삭제·목록 추가·삭제·정렬) 뒤마다 전체 스캔과 같아요. 알리지 않은 변경은 샘플 재구성에서 잡혀 색인이 꺼져요.
- 서비스 관련 검사 15종 통과(애니메이션 예산·몽타주 4종·파티클 2종·그래프·리타게팅·큐 VFX·입력·워크플로·거리 LOD·리비전 검증 5종).
  - `check-gameplay-cues-2528`, `check-runtime-features`는 직전 커밋에서도 같은 이유로 실패해요.
- 측정(3D 1만 개, 프로브 없는 장면, 400프레임, 교대 2회): 직전 커밋 28.1·26.2ms → 16.1·14.7ms.

### 화면 밖 그룹 승격·호출 비용 정리 (2026-11-14)

- **화면 밖 그룹도 호스트로**
  - 화면 밖 칸에 표시된 구성원, 그리고 그룹별로 건너뛰는 화면 밖 그룹은, 인코딩마다 최대 512개를 방문해요(그리기는 만들되 화면에 그리지 않음).
  - 리비전이 처음 보거나 30번 이상 지난 그룹만 방문해서, 그룹마다 대략 두 번 방문하면 호스트 집합으로 옮겨가요.
  - 그림자 때문에 방문만 하는 그룹(화면 밖)도 묶음 후보로 봐요. 호스트 소유 그룹은 정적 칸에서 빠져요.
  - `check-host-static-sets`를 300프레임으로 늘렸어요. 400개 모두(화면 밖 포함) 옮겨지고, 메인 패스는 매 프레임 같아요.
- **카메라 선택:** 목록·컴포넌트가 바뀔 때(그리고 64번째 호출마다)만 카메라 후보를 다시 찾아요(`componentRevisionSerial`).
- **물리 `ready`:** 3D만 있는 게임에서 매 프레임 2D 충돌체를 찾던 전체 순회를, 목록·컴포넌트가 바뀔 때(그리고 64번째마다)만 해요.
- **정적 행렬 갱신:** 깨끗함이 확인된 기록은 오브젝트 변경 알림·부모 변경·실제 갱신 전까지 리비전 비교를 건너뛰어요. 기록은 그룹 속성으로 바로 읽어요(WeakMap 조회 없음).
- 측정(1만 개, 단일 실행)
  - 3D(프로브 없음): 프레임 작업 중앙값 8.75ms. 직전 측정에서는 7.18ms, JS 128FPS, 화면 192FPS였어요.
  - 3D(반사 프로브): 48.4ms
  - 2D: 40.3ms
- 다음: 반사 프로브 장면과 2D 스프라이트를 호스트로(2단계).

### 2단계-1: 반사 프로브 장면 (2026-11-15)

- 반사 프로브가 있어도 호스트 집합을 써요.
  - 프로브 캡처 면에는 구성원 상자 합집합이 그 면과 겹치는 집합을 넣고, 호스트는 전체 행을 그려요(면 밖은 래스터에서 잘려요). 집합은 면 목록 앞에 둬요.
  - 승격한 프레임에는 그 그룹의 개별 ID를 프로브 목록에서도 빼요.
  - 집합 템플릿의 전역 프로브 필요 여부를 프레임 판단에 넣어요.
  - 프로브 위치·범위·세기처럼 바인딩에 쓰이는 값이 바뀌면 모든 그룹을 강등해요(바인딩은 다음 방문에서 다시 계산). 캡처 설정(해상도·갱신 번호 등)만 바뀌면 그대로 둬요.
- 검사 `check-host-static-sets`에 반사 프로브 장면을 추가했어요(300프레임).
  - JS는 프로브 상자로, 호스트는 구로 컬링해요. 그래서 상자와 구가 모두 화면과 겹치는 "실제로 보이는" 행끼리 비교해요. 메인 패스가 매 프레임 같아요.
  - 프로브 면 30개에서 A가 면 안에 그리는 행을 B도 모두 그려요.
- 실제 D3D12: 반사 프로브 장면 묶음·정적 비교에서 호스트 집합 9개(보이는 행 272개)로 픽셀 최대 차이 1(허용 범위)이에요. 프로브 없는 장면은 0이에요.
- 측정(3D 1만 개, 반사 프로브, 600프레임 단일 2회): 48.4ms → 6.49·8.51ms(실제 화면 185·149FPS).

### 2단계-2: 2D 준비 줄이기 (2026-11-15)

- 2D 정렬: 루트 항목을 지난 프레임의 정렬 순서로 시작해요. 캐시 항목은 같은 객체라 거의 정렬된 한 덩어리를 걷는 정렬이 돼요. 비교가 전체 순서라 결과는 시작 순서와 무관해요.
- 표시 색 개수를 쓰지 않는 네이티브 렌더러에서는 머테리얼 수 세기와 표시 확인을 건너뛰어요.
- 반사 프로브 찾기는 정적 대상 그룹(static-groups 대상: 평범한 메시·허용 컴포넌트만)의 하위 트리도 걷지 않아요.
- 측정(2D 1만 개, 600프레임 단일 2회): 40.3ms → 36.3·32.2ms.
- 남은 2D 비용: 보이는 스프라이트마다 그리기 방문, 화면 밖 스프라이트의 그룹별 생략, 2D 준비의 그룹 순회, 2D 조명 수신자마다 유니폼 쓰기.
- **2D 호스트화 설계(다음)**
  - 직교 카메라에서 움직이지 않는 스프라이트끼리의 정렬 순서는 카메라 이동에 변하지 않아요(깊이가 모두 같은 값만큼 바뀜).
  - 정적 스프라이트를 정렬된 한 줄로 호스트에 두고, 같은 상태가 이어지는 구간을 순서 보존 컬링 집합으로 만들어요.
  - 움직이는 스프라이트는 이분 탐색으로 끼어들 자리를 찾아, 그 자리에서 집합을 범위로 나눠 그려요(호스트 범위 그리기 필요).
  - 2D 조명을 받는 스프라이트는 조명 설정이 그리기 기록에 들어가므로, 2D 조명 자료(광원 텍스처·수신 설정)도 호스트에서 공유하도록 옮겨야 해요.

### 2단계-3: 2D 호스트 집합 (2026-11-15)

- **셰이더:** 2D 조명의 빠른 노멀 모드가 쓰는 오브젝트 원점을 그리기·인스턴스 월드 행렬에서 읽어요(`TEXCOORD7`). JS는 2D 설정의 원점 xy를 보내지 않아서, 조명 받는 스프라이트도 같은 상태로 묶여요.
- **브리지 구간 그리기:** 그리기에 `cullRange:[start,end)`를 줄 수 있어요. 컬링은 구간 안에서 행 순서를 지켜 하고, 보이는 행 버퍼는 그리기마다(`id#view`) 따로 있어요. 지운 그리기의 버퍼도 함께 지워요.
- **JS 2D 집합**
  - 3D 그림자를 드리우지 않는 투명 스프라이트만 있는 깨끗한 정적 그룹을, 묶음 상태 키별 2D 집합으로 올려요. 집합의 행은 렌더 순서대로예요.
  - 매 프레임 올린 스프라이트의 `renderOrder`(2D 정렬이 배정)가 전체 순서에서 계속 증가하는지 확인해요. 아니면 순서와 구간을 다시 만들고, 바뀐 집합은 다시 보내요.
  - 같은 집합이 연속한 구간을 범위 그리기로 내보내요. 올리지 않은 투명 항목의 순서가 구간 안에 들어오면 그 자리에서 나눠요. 순서 값이 같은 경우는 다음 프레임부터 그 그룹을 원래 경로로 돌려요.
  - 집합마다 매 프레임 구성원 머테리얼에서 2D 설정(광원 수·광원 텍스처·마스크)을 다시 읽어, 바뀌면 템플릿을 갱신하고 텍스처 업로드를 유지해요.
  - 2D 준비는 2D 호스트 그룹을 건너뛰지 않아요(렌더 순서 배정이 필요해요).
- **검사**
  - `check-host-2d-sets`(신규): 260프레임 동안 순서를 포함한 메인 패스가 같아요. 정적 스프라이트 300개(상태 2종 섞임, 구간 최대 189개), 정적 스프라이트 사이를 움직이는 스프라이트 3개, 카메라 이동, 알린 이동·숨김·정렬 순서 변경을 포함해요. 나누기를 끄는 변이는 15프레임에서 잡혀요.
  - `check-native-sprite-batch-gpu host`(신규 모드): 실제 D3D12 150프레임 화면이 픽셀 차이 0이에요(2D 점광·전역광, 조명·비조명·가산 혼합, 2D 집합 12개, 364행). 묶음 모드도 차이 0이에요.
- 측정(2D 1만 개, 600프레임 단일 2회): 32.2~36.3ms → 15.4·18.1ms(실제 화면 78·68FPS).
- 남은 2D 비용: 2D 준비(스프라이트마다 정렬 항목 갱신·전체 정렬·렌더 순서 배정·조명 수신자 유니폼) 약 26%, 행렬 갱신 약 9%.

### 2단계-4: 증분 2D 정렬 (2026-11-15)

- **2D 정적 정렬 블록**(`TwoDRendering.block`)
  - 직교 카메라에서 바뀌지 않은 정적 스프라이트는 서로의 순서가 유지돼요(카메라가 움직이면 카메라 깊이가 모두 같은 값만큼 바뀌어요).
  - 그 항목과 `renderOrder`는 그대로 두고, 나머지 항목만 만들고 정렬해요. 그 뒤 이분 탐색으로 블록 사이에 넣고 소수 `renderOrder`를 줘요. 카메라 깊이는 블록을 만든 카메라 기준으로 옮겨서 비교해요.
  - 블록을 다시 만드는 경우: 블록 오브젝트의 변경 알림, 그룹 구성 변화(블록 그룹 수 불일치), 카메라 방향·레이어 목록 변화, 정렬 그룹 등장, 표시 색 집계, 검증 모드·정적 끄기, 64번째 프레임
  - 마스크·파티클·정렬 그룹 항목은 블록에 넣지 않아요.
- **2D 조명:** 블록 수신자의 유니폼은 프레임 공통 값(광원 데이터·개수·쿠키·도형·그림자 아틀라스·모드·채널)이 바뀔 때만 다시 써요. 수신 레이어는 블록 것까지 합쳐요.
- 검사 `check-two-d-sort-block`(신규)
  - 직교 2D 404개, 200프레임. 렌더 순서로 정렬한 스프라이트 순서가 전체 정렬과 매 프레임 같아요.
  - 움직이는 스프라이트, y·카메라 깊이, 레이어·순서 섞임, 카메라 xy·z 이동, 알린 이동·정렬 변경, 그룹 제거를 포함해요.
  - 깊이 보정을 끄는 변이는 41프레임에서, 변경 알림을 끄는 변이는 100프레임에서 잡혀요.
- 실제 D3D12 `check-native-sprite-batch-gpu`(기본·host): 픽셀 차이 0이에요.
- 측정(2D 1만 개, 600프레임 단일 2회): 15.4~18.1ms → 9.77·8.98ms(실제 화면 130·142FPS). 2D 준비는 프레임의 약 3%예요.

### 공통 비용 정리 (2026-11-15)

- **두 번째 장면 행렬 갱신 생략:** 2D 준비가 장면 행렬을 갱신한 뒤 알린 변경이 없고(`revisionSerialNow`) 프레임 시각 갱신도 없으면, 인코딩은 다시 갱신하지 않아요. 64번째마다와 검증 모드에서는 갱신해요.
- **파티클 틱:** 실행기는 전체 목록 대신 등록된 파티클 그룹만 돌아요(`tickParticles(...,{all:true})`).
- **데칼:** 데칼 그룹을 프레임 시각으로 등록하고, 하나도 없으면 데칼 동기화가 전체 그룹을 훑지 않아요.
- **컴포넌트 색인**
  - 표본 재구성은 동기화 512번에 한 번 해요(서비스가 프레임당 여러 번 동기화해요).
  - `list.length=0`처럼 감시 함수를 거치지 않는 목록 변경도 길이 비교로 잡아요. 카메라 후보와 물리 차원 확인에도 같은 비교를 넣었어요.
- **수정:** 컴포넌트 색인 커밋(52ad8ee0) 이후 실패하던 `check-multi-emitter-2938`(목록을 길이로 비운 뒤 지난 오브젝트의 파티클 요청)을 고쳤어요. 파티클 시작 기록 정리 루프는 Cue 항목까지 지울 수 있어서 뺐어요(64프레임 전체 순회가 정리해요).
- 측정(1만 개, 600프레임 단일 2회)
  - 3D(프로브 없음): 5.56·6.69ms(JS 168·135FPS, 실제 화면 233·187FPS)
  - 2D: 7.17·6.90ms(실제 화면 180·181FPS)

### 행렬 갱신 부모 루프·대상 목록 캐시 (2026-11-15)

- **부모 단위 행렬 갱신:** 감시 그룹의 부모(three 기본 갱신을 그대로 쓰는 부모)에 같은 동작의 갱신을 설치해요. 단위행렬 부모 아래에서 깨끗함이 확인된 정적 자식은 호출 없이 건너뛰어요. 표본 실제 갱신(sampleEvery)은 그대로예요.
- **대상 목록 캐시**(`objectsWhere`, `objectMapOf`): 목록(감시 함수·길이)과 알린 컴포넌트가 같으면 컴포넌트로 거른 목록과 id 지도를 다시 써요. 64번째 호출마다 다시 만들어요.
  - 적용: 장면 환경(환경 액터·태양), 후처리 볼륨, AI 감지 틱
- 측정(1만 개, 800프레임 단일 2회)
  - 3D(프로브 없음): 1.62·1.56ms(JS 461·457FPS, 실제 화면 630·639FPS)
  - 2D: 2.38·2.14ms(실제 화면 409·456FPS)
- 10만 개(3D, 프로브 없음): 장면 준비 중 JS 힙 4GB 한도를 넘어 실행기가 종료돼요("JavaScript heap out of memory", 시작 후 약 82초). 오브젝트당 JS 메모리가 수십 KB예요. 다음 과제는 오브젝트당 메모리 줄이기(장면 오브젝트·three 그룹·그리기 기록·정렬 항목·리비전/정적 기록)와 준비 시간 줄이기예요.

### 10만 개 실행 비용 (2026-11-15)

- 차량 물리 동기화: 물리 sync마다 모든 오브젝트의 컴포넌트를 걸렀어요(10만 개에서 36%). 캐시된 대상 목록으로 바꿨어요.
- 물리 단계의 `objects.find(o=>o.id===…)` 5곳(게임모드·컨트롤러·부모 찾기): 캐시된 id 지도(`objectMapOf`, 같은 id면 첫 오브젝트)로 바꿨어요.
- `vm.object(id)`: 빈 id(undefined·null)는 전체를 훑지 않고 바로 없음을 돌려줘요. 다른 경우는 인덱스 교체·이름 변경까지 원래와 같아야 해서 그대로 둬요.
- 실행 종료: 오브젝트마다 `vm.object`로 몽타주 주인을 찾던 제곱 비용을, 한 번 만든 id→첫 오브젝트 지도로 바꿨어요.
- 측정(600~1500프레임 단일)
  - 3D 10만 개(프로브 없음): 프레임 작업 중앙값 188ms → 35.8ms, 실제 화면 27→33FPS, RSS 약 2.9GB
  - 3D 1만 개: 1.44ms(실제 화면 713FPS)
- 10만 개에 남은 비용: 프레임마다 10만 그룹을 한 번씩 보는 가벼운 순회들이 쌓여요(그리기 순회 자식 루프, 부모 행렬 루프, 2D 준비 사전 순회, 호스트 미방문 확인, 물리 sync). 이걸 없애려면 호스트·정적 그룹을 한 컨테이너 아래로 모아 통째로 건너뛰는 장면 구조가 필요해요.

- 컨테이너 동작
  - 컨테이너에 다른 것을 넣으면(재생성한 교체 그룹 등) 원래 부모로 넘겨요.

- 측정(3D 10만 개, 프로브 없음, 1500프레임): 프레임 작업 중앙값 35.8ms → 7.64ms(실제 화면 132FPS, RSS 약 3.4GB)

### 10만 개 240FPS (2026-11-15)

- **물리 전체 동기화 주기:** 표본 창(동기화마다 64개)이 모든 오브젝트를 한 번 도는 주기에 맞춰 `max(30, 오브젝트 수/64)`번마다 해요. 목록·머테리얼·변형체 변화와 신뢰 꺼짐에서는 그대로 바로 해요.
- **그룹 목록 재사용:** 실행 장면의 비주얼 그룹 지도는 변경 번호를 가져요. 실행기의 `all()`은 같은 번호 동안 같은 배열을 돌려줘요.
- **2D 준비:** 네이티브 렌더러는 호스트 컨테이너에 든 그룹을 뺀 목록을 받아요(그룹 목록·컨테이너 구성이 바뀔 때 다시 만들어요). 표시 색 개수와 텍스처 스트리밍은 전체 목록을 그대로 써요.
- **집합 추가분 전송(`cullSetAppend`):** 승격으로 구성원만 늘어났으면 새 행과 구만 보내고, 호스트가 집합 끝에 붙여요(전체 행 버퍼는 호스트에서 다시 만들어요). 구성원이 빠지면 전체를 다시 보내요.
- 검사 `check-host-static-sets`에 추가분 전송 확인을 넣었어요(4회 사용, 결과 동일).
- 실제 D3D12 `check-native-mesh-batch-gpu` host·기본, `check-native-sprite-batch-gpu` host 통과.
- 측정(3D 10만 개, 프로브 없음, 1500프레임)
  - 프레임 작업 중앙값 7.64ms → 2.20ms
  - 실제 화면 132 → 373FPS, RSS 약 3.1GB
  - p95 23ms, p99 137ms: 승격 과정(인코딩당 512개)과 GC 구간이 섞여 있어요.

### 급증 프레임 줄이기 (2026-11-15)

- 원인(10만 개, 프레임별 기록)
  - 64프레임마다 약 150ms: 게임 서비스의 안전 확인용 전체 순회(오브젝트마다 await 포함)
  - 64번째 호출마다 15~40ms: 캐시된 대상 목록(환경·후처리·AI·차량), 카메라 후보, 물리 차원 확인이 10만 개를 다시 거름
- 고친 것
  - 컴포넌트 색인 검증을 순환식으로 바꿨어요. 동기화마다 256개의 컴포넌트 종류를 다시 읽어 비교하고, 다르면 보고하고 색인을 꺼요.
  - 색인을 믿을 수 있는 동안 서비스는 전체 순회를 하지 않아요. 흔들림·번쩍임 상태는 매 프레임 목록의 1/64를 돌아가며 확인해요.
  - 대상 목록·카메라 후보·물리 차원 확인의 64번째 재구성을 없앴어요. 대신 색인 검증이 불일치를 찾으면 `listCacheConfig`가 바뀌어 모두 다시 만들고, 그 뒤로는 매번 다시 만들어요.
- 측정(3D 10만 개, 1500프레임, 400프레임 이후)
  - 이전: 중앙값 2.2ms, p95 23ms, p99 137ms, 최대 160ms
  - 지금: 중앙값 2.55ms, p95 4.4ms, p99 5.2ms, 최대 12.9ms(실제 화면 551FPS)
  - 0~400프레임은 장면 준비와 호스트 승격 구간이에요.

### 로딩 구간 줄이기 (2026-11-15)

- 측정 도구: `HB_CPU_PROFILE_FROM=boot`(FPS 측정 `HB_FPS_CPU_FROM=boot`)이면 CPU 프로필이 시작 준비 구간도 담아요.
- 고친 것
  - **고정 접촉:** 고정 몸체·충돌체가 바뀔 때만(`space.fixedVersion`) 다시 계산해요. 움직이는 몸체의 자세 변경으로는 다시 계산하지 않아요. 쌍 쓸기는 배열 할당 없이 거리 제곱으로 걸러요.
  - **컨테이너 이동:** 한 인코딩에 승격한 그룹을 모아, 부모 자식 목록을 한 번에 줄이고 컨테이너로 옮겨요(하나씩 빼면 매번 자식 목록 전체가 당겨졌어요).
  - **승격 나이:** 정적 칸에 들어갈 때 호스트 나이를 기록해서, 화면 밖 그룹은 강제 방문 한 번으로 승격돼요. 강제 방문 한도는 인코딩당 4096개예요.
  - **컴포넌트 기본값 복사:** `structuredClone` 대신 JSON 형태 자료용 직접 복사를 써요.
- 측정(3D 10만 개, 프로브 없음)
  - 첫 프레임: 13.5초 → 5.5초
  - 정상 상태 도달: 약 300프레임 → 50프레임
  - 1~50프레임 작업 합: 약 20초
  - 측정 실행 전체(패키징 포함): 95초 → 61초

### 로딩 더 줄이기 (2026-11-15)

- **승격 대기 단축**
  - 렌더러 첫 인코딩 이후 한 번도 바뀌지 않은 오브젝트(`hostBorn`)는 기다리지 않아요.
  - 그 밖에는 "30번 인코딩 또는 0.5초 중 먼저"예요(로딩 중 느린 프레임에서 30번이 몇 초가 되던 문제).
  - 강제 방문 한도는 정적 칸에서 기다리는 그룹 수의 1/8(최소 4096)이에요(이후 1/4로 바꿈, 아래 "가벼운 승격 경로" 참고).
- **물리 정적 비교기:** 표본 확인에서 처음 쓸 때 만들어요(로딩 때 10만 개를 미리 만들지 않아요).
- **id 지도:** 컴포넌트 변경 번호와 무관하게 목록 변화에만 다시 만들어요.
- 측정(3D 10만 개, 프로브 없음)
  - 1~50프레임 작업 합: 약 20초 → 6.4초
  - 정상 속도 도달: 50 → 19프레임
  - 첫 프레임 6.0초(그중 첫 인코딩 5.0초)
  - 측정 실행 전체(패키징 포함): 61초 → 48초
- 남은 로딩: 첫 인코딩이 10만 그룹마다 처음 한 번 하는 일(깨끗함·경계·화면 판정·칸 등록)과 장면·물리 구축이에요. 더 줄이려면 첫 인코딩을 여러 프레임에 나눠야 해요.

### 첫 인코딩 나누기(분석과 결과)

- 첫 프레임 분석(3D 10만 개, 프로브 없음, CPU 프로파일)
  - JS 첫 인코딩은 약 1초였어요. 나머지는 네이티브 첫 렌더 명령(약 2.2초)과 대기였어요.
  - 네이티브 2.2초 중 약 1.9초는 새 사용자 프로필의 첫 셰이더 컴파일이에요. 400개 장면에서도 같아서 오브젝트 수와 무관해요(디스크 캐시가 있으면 다음 실행부터 줄어요).
  - 나머지 네이티브 비용은 같은 프레임에 승격된 그룹의 개별 그리기 갱신이었어요. 호스트는 각 레코드를 만들었다가 다음 프레임에 지웠어요.
- **승격 그룹의 개별 갱신 제외:** 이번 인코딩에서 승격된 그룹의 그리기 갱신은 보내지 않아요(집합이 이미 행을 가져요). 다음 프레임의 제거 목록은 그대로라 기록 정리는 같아요.
- **objectsWhere 증분 재검사:** 컴포넌트 알림만 있었으면(목록·길이·에포크 같음, 최근 65536개 알림 기록 안) 알림된 오브젝트만 다시 검사하고, 들어오거나 나가는 오브젝트가 있을 때만 다시 만들어요. 로딩 중 머티리얼 준비 알림마다 10만 개를 거르던 차량 동기화가 빠졌어요(로딩 프레임 런타임 약 170 → 60ms).
- 측정(같은 날, 같은 장면)
  - 첫 프레임: 4.65초(프로파일 켬) → 3.4초(프로파일 끔). 그중 네이티브 셰이더 컴파일이 약 1.9초예요.
  - 정상 상태: 중앙값 2.6ms, 실제 화면 539FPS(변화 없음).
- 남은 로딩: 1~17프레임(프레임당 300 → 100ms)은 화면 밖 그룹의 강제 방문 승격이에요. 그룹마다 그리기 기록·상태 키(JSON)를 처음 만드는 비용이라, 줄이려면 화면 밖 그룹용 가벼운 승격 경로가 필요해요. 첫 실행 셰이더 컴파일은 비동기 파이프라인 준비가 필요해요.

### 가벼운 승격 경로(로딩 꼬리)

- 프레임별 기록으로 원인을 찾았어요. 로딩 꼬리 17프레임 동안 승격은 늘 프레임당 정확히 4096개였어요.
- **정적 칸 항목 검사 수정:** 한 번도 방문하지 않은 그룹은 `drawCache`가 `undefined`인데 칸 항목은 `null`을 들고 있었어요. 그래서 `staticEntryValid`가 늘 실패했어요.
  - 매 프레임 칸 멤버 약 6.5만 개가 빠졌다가 다시 등록됐어요(`admitStatic`·`markStaticCells` 비용).
  - 대기 수는 늘 약 3500으로 보여 강제 방문 한도가 최소값 4096에 묶였어요.
  - 이제 `drawCache ?? null`로 비교해요.
- **강제 방문 한도:** 기다리는 그룹 수의 1/4(최소 4096)이에요.
- **승격 상태 키:** JSON 문자열 대신 값 단위로 비교해요. 같은 구간(부분 범위·첫 맵)의 알려진 상태와 비교하고, 마지막으로 맞은 상태를 먼저 봐요. 새 상태는 계속 증가하는 번호를 받아요(예전에는 4096개를 넘으면 번호가 다시 1부터 시작해 이미 붙은 키와 겹칠 수 있었어요).
- **반사 프로브가 없으면 승격 행의 프로브 AABB를 계산하지 않아요.** 프로브가 생기면 프로브 키 변화로 모든 그룹이 돌아가요.
- 측정(3D 10만 개, 프로브 없음)
  - 로딩 꼬리: 17프레임 → 9프레임
  - 1~50프레임 실제 시간 합: 7.1초 → 5.3초
  - 첫 프레임: 3.2초
  - 정상 상태: 중앙값 2.56ms, 실제 화면 576FPS
- 10k A/B(커밋 전 코드와 번갈아 측정): 3D 중앙값 1.53~1.63ms 대 1.56~1.60ms, 2D 2.57~2.63ms 대 2.52~2.61ms로 측정 오차 안이에요. 오늘 이 기계는 이전 기록(3D 1.17ms)보다 전체적으로 느렸어요.

### 2D 최적화

- **2D 호스트 그룹도 컨테이너에 넣어요.** 2D 준비는 장면 자식이 아니라 그룹 목록을 정렬하므로 순서가 그대로예요. 그리기 순회·부모 행렬 루프·미방문 확인에서 빠져요.
- **컨테이너 검사는 인코딩당 한 번이에요.** 2D 준비·조명·인코딩이 한 프레임에 장면 행렬 갱신을 여러 번 불러, 매번 4096개 창을 검사하던 비용이 빠졌어요. 부모가 항등 행렬이 아니면 매번 검사해요. 3D에도 같이 적용돼요.
- **스프라이트 판 지오메트리를 크기별로 공유해요.** 크기는 최대 4096종이고, 공유본은 해제하지도 그 자리에서 고치지도 않아요.
  - 스프라이트 리그가 붙거나 스킨이 있는 그룹은 자기 복사본을 써요.
  - 2D 10만 개에서 네이티브 메시가 10만 개에서 2개로 줄었어요. 메시가 많아 네이티브 `reset`이 20초 걸려 응답 시간 초과로 끝나던 문제(이전부터 있었어요)도 없어졌어요.
- **2D 정렬 블록의 64프레임마다 전체 재정렬을 없앴어요.** 10만 개에서 약 200ms 급증 프레임이었어요.
  - 대신 컴포넌트 색인이 알리지 않은 변경을 찾으면(`listCacheConfig.epoch`) 블록을 버려요.
  - 알리지 않은 이동은 정적 그룹 표본 검사가 정적 건너뛰기를 끄면서 블록도 버려요.
- **호스트 2D 순서 확인:** 모든 멤버가 현재 정렬 블록(`renderer.hbTwoDBlock`)에 있고 한 번 증가 순서로 확인됐으면, 블록이나 순서가 바뀔 때까지 매 프레임 10만 개 확인을 건너뛰어요.
- **objectsWhere로 바꾼 곳:** 물리 차원 스캔, 게임 카메라 후보. 이제 알림된 오브젝트만 다시 검사해요.
- **컴포넌트 색인 순환 검증:** Set을 만들지 않고 비교하며, 동기화 4번에 한 번 진행해요.
- **진단:** 자원 해제 실패 메시지에 내부 오류(스택)를 붙여요.

### 첫 프레임 셰이더·파이프라인 비동기 준비(D3D12)

- **원인:** 첫 프레임 네이티브 1.7초는 HLSL 컴파일(합쳐 약 130ms, 디스크 캐시)이 아니었어요. 메인 픽셀 셰이더의 첫 그래픽 파이프라인(PSO)을 드라이버가 만드는 시간(약 1.27초)이었어요. 같은 셰이더의 다음 PSO들은 15~47ms예요.
- **비동기 PSO 생성:** 비동기 준비가 켜지면 기본(프로그램이 아닌) PSO를 작업 스레드에서 만들어요(`std::async`, D3D12 장치의 PSO 생성은 스레드 안전).
  - 준비 전에는 그 그리기만 건너뛰고, 래스터 준비가 `pending`으로 보고돼요. 그동안 브리지와 JS는 그림자·프로브를 미루고, 준비되면 다시 그려요.
  - 머티리얼 프로그램 PSO는 지금처럼 동기예요.
- **미리 시작:** 비동기 준비가 켜지는 순간(렌더러 초기화) 기본 셰이더별 첫 PSO(메인 HDR·표면·그림자)를 시작해요. 그래서 장면 로딩과 겹쳐요.
- **게임 실행기도 D3D12 비동기 준비를 켜요.** 편집기와 D3D11은 이미 켜져 있었어요.
  - 실행기는 첫 게임 프레임 전에 준비 완료를 기다리면서 25ms마다 화면을 다시 그려요. 창이 멈추지 않고, 게임 로직은 준비된 뒤 시작해요.
- 측정(이 기계, NVIDIA)
  - 10만 개 3D 첫 프레임: 3.1초 → 1.8초(네이티브 첫 렌더 명령 1.77 → 0.36초)
  - 400개: 첫 렌더 명령 1.72 → 0.44초. 첫 게임 프레임은 PSO 준비를 기다려 1.7초 그대로예요(로딩이 짧아 겹칠 시간이 적어요).
- **다른 컴퓨터 대응**
  - 코드 측면:
    - PSO 비동기 생성은 D3D12 표준 동작이라 특정 GPU에 기대지 않아요.
    - 드라이버가 PSO를 빨리 만들면 대기가 그냥 짧아질 뿐이에요.
    - 오늘 바꾼 성능 수치(창 4096개, 한도 비율 등)는 하드웨어 측정값이 아니라 알고리즘 상수예요.
  - 검증 범위:
    - 이 기계(NVIDIA)에서 D3D11·D3D12-11on12·D3D12 세 백엔드가 같은 그리기 수로 동작했어요.
    - 하드웨어 실패 시 WARP(소프트웨어) 대체 검사(`check-native-device-fallback`)가 통과했어요.
  - 미검증:
    - AMD·Intel GPU, 저사양 기계, 다른 Windows 버전의 실제 실행은 아직 확인하지 않았어요.
    - FPS 수치는 이 기계 기준이에요.

### 프로브 장면

- 호스트 집합은 프로브 장면에서도 이미 켜져 있었어요(1만 개에서 집합 13개).
- **차이의 원인:** 프로브가 있으면 화면 밖 메시도 캡처용 그리기를 만들었어요. 그래서 화면 밖에서 움직이는 하늘 구름(구 30개)이 매 프레임 다시 만들어지고, 네이티브로 약 39KB씩 전송됐어요.
- **수정:** 이번 프레임에 캡처가 있을 수 있을 때만 그 메시들을 만들어요.
  - 캡처가 있을 수 있는 경우: `onChange` 프로브가 있거나, 프로브의 캡처 키가 바뀌었을 때(새로 생김·이동·설정·갱신 요청·머티리얼 준비로 캐시 비움).
  - 기본값 `once`·`manual` 프로브는 키가 바뀌는 프레임에만 캡처하므로 결과가 같아요.
  - 정적 그룹 캐시를 기록할 때는 모두 만들어서 캐시된 프로브 항목이 빠지지 않아요.
- 측정(D3D12)
  - 프로브 1만 개: 877 → 1237FPS(프로브 없는 장면과 같음)
  - 프로브 10만 개: 615 → 780FPS
  - 프레임당 그리기 갱신: 30 → 0
- 원래부터 실패하던 검사(커밋된 코드에서도 같음): `check-probe-capture-key-352`, `check-probe-room-991-native`.

### 움직이는 물체(물리)

- **측정 장면:** `check-native-backend-fps.mjs`에 `HB_FPS_MOVERS`(움직이는 물체 수)를 추가했어요. 고르게 고른 메시에 중력 없는 동적 Rigidbody와 시작 속도를 주어 계속 움직이고 서로 부딪혀요.
- **처음 측정:** 1만 개 중 1000개만 움직여도 48FPS였어요. 물리 step이 프레임당 272ms(sync 121ms)였고, 렌더는 20ms였어요.
- **원인과 수정**(모두 JS)
  - **충돌체 재생성(정확성 문제 포함):**
    - 원인: 회전하는 물체는 월드 행렬 분해로 얻은 크기가 끝자리에서 흔들려요. 그 값이 충돌체 서명에 들어가서, 매 동기화마다 충돌체를 지우고 다시 만들었어요. 그때마다 접촉 정보도 초기화됐어요.
    - 수정: 루트 물체는 작성된 크기(`o.scale`)로 서명해요.
  - **물리 이동 반영:**
    - 원인: 서브스텝마다 `update`가 컴포넌트 변경을 알리고(touchComponents), 스프라이트·머티리얼 동기화까지 했어요. 그래서 모든 리비전 캐시가 계속 무효화됐어요.
    - 수정: 물리 전용 `moved` 콜백을 추가했어요. 위치 변경 알림과 메시 변환만 해요. 게임 런타임 `run-project`가 제공하고, 없으면 `update`를 써요.
  - **JSON 없는 비교:** 강체 설정과 충돌체 서명은 알린 컴포넌트가 그대로이면 다시 만들지 않아요.
    - 게임 런타임(`staticCache`)에서만 적용하고, 신뢰 상태·검증 모드 아님이 조건이에요.
    - 표본 동기화에서는 전부 확인하고, 알리지 않은 변경을 찾으면 보고한 뒤 물리 신뢰를 꺼요.
    - 속도·자세 키는 배열로 비교해요. 접촉 키도 JSON 대신 문자열을 이어 붙여요.
  - **바뀐 것 없는 강체 건너뛰기:** 컴포넌트·충돌 플래그·머티리얼 수·루트 자세 입력·속도가 마지막 전체 처리(또는 물리가 직접 쓴 값)와 같으면 sync에서 건너뛰어요. 이것도 표본으로 확인해요.
  - **자세 재사용:** `updateObjects`가 쓴 자세와 입력을 기록해서, 다음 sync가 다시 분해하지 않아요.
- 측정(1만 개 장면, D3D12)

| 움직이는 물체 | 이전 | 지금 |
|---|---|---|
| 100개 | – | 중앙값 3.36ms, 실제 화면 413FPS |
| 1000개 | 물리 272ms/프레임, 48FPS | 물리 58ms/프레임, 중앙값 74ms |

  - 1000개 장면은 프레임이 느려 서브스텝이 5번 돌아요. 정적 장면(3D 0.97ms, 2D 0.91ms)은 그대로예요.
- **남은 것:**
  - 접촉 수집: 서브스텝마다 움직이는 모든 충돌체의 WASM 콜백을 돌고, 서브스텝마다 충돌 이벤트가 쓰여요. 접촉 시작·종료 이벤트로 활성 쌍만 유지하는 방식이 필요해요.
  - `updateObjects`: 강체마다 자세 분해와 객체 생성을 해요.
  - 렌더: 움직인 그리기 1000개를 매 프레임 전송해요.

### 접촉 수집

- 움직이는 충돌체의 접촉·교차 상대 목록을 "관련 충돌체" 찾기 단계에서 한 번만 조회하고, 수집 단계에서 그대로 재사용해요. 같은 상태에서 같은 질의를 하므로 순서도 같아요.
- 양쪽 충돌체에서 각각 도달하는 쌍은 한 번만 조회해요. 접촉이 없으면 반대쪽에서 다시 물어도 답이 같아요.
- 위치는 실제 접촉일 때만 읽어요.
- 동기화에서 건너뛴 강체는 동기화 끝의 미러링(속도·디버그 정보)을 하지 않아요. 이미 강체 값과 같아요.
- 측정(1만 개 중 1000개 이동)
  - 물리 58 → 39ms/프레임, 서브스텝 5 → 4
  - 프레임 중앙값 74 → 55ms
- **남은 한계:** 1000개가 계속 부딪히는 장면은 실제 접촉 쌍이 많아요. 강체·쌍마다 Rapier(WASM)와 JS 사이를 오가는 호출 비용이 서브스텝당 약 10ms예요.
  - 크게 줄이려면 물리 동기화를 한 번에 주고받는 일괄 경로가 필요해요(강체 자세·속도를 버퍼로 읽고 쓰기).
  - 또는 물리를 네이티브(C++)로 옮겨야 해요.

### 물리 일괄 경로(현재 Rapier API 안에서)

- 설치된 Rapier는 수정되지 않은 0.21 WASM이라 강체 자세·속도를 버퍼로 한 번에 읽는 API가 없어요. 그래서 진짜 일괄 읽기는 Rust로 WASM을 다시 빌드하거나 네이티브 물리가 필요해요.
- 지금 API 안에서 JS↔WASM 호출을 줄였어요.
  - **깨어 있는 강체:** 공간마다 `islands.forEachActiveRigidBodyHandle` 한 번으로 받아요. 강체마다 하던 `isFixed`·`isSleeping` 호출 2번이 빠졌어요. 키네마틱은 깨어 있는 것으로 봐요.
  - **미러링:** 질량·CCD 값은 충돌체·설정이 바뀔 때만 다시 읽어요. 잠김 상태는 호출한 쪽이 알 때 넘겨요.
  - **물리 결과 반영 순서:** 강체 레코드 구성이 바뀔 때만(부모가 있는 강체가 있으면 매번) 다시 만들고 정렬해요.
- 측정(1만 개 장면)
  - 1000개 이동: 물리 39 → 27ms/프레임, 서브스텝 4 → 3, 프레임 중앙값 55 → 41ms
  - 100개 이동: 3.36 → 1.25ms, 실제 화면 413 → 562FPS
- **남은 것:**
  - 렌더: 움직인 그리기를 매 프레임 전체 레코드(1000개 약 1.3MB JSON)로 보내요. 행렬만 바뀐 그리기는 행렬만 보내는 경로가 필요해요(C++ 변경).
  - 물리: 강체마다 자세 분해, 접촉 쌍 질의, Rapier step이 남아 있어요.

### 행렬만 전송

- 보관된 그리기의 바뀐 값이 world·normal 행렬뿐이면 전체 레코드(약 1.3KB JSON) 대신 보내요.
  - 조건: 상태·머티리얼·인스턴스 값(색·UV)이 같고, 호스트가 이전 레코드를 가지고 있어야 해요.
  - 형식: `drawTransforms` 자원 하나에 id 목록과 그리기당 float64 행 32개(world, normal)를 담아요.
  - 네이티브는 업로드 단계에서 기존 그리기의 world·normal·previousWorld를 바꿔요.
  - 그림자·프로브 갱신 판단은 기존 스탬프를 그대로 써요.
- float64로 보내서 JS 쪽 값이 전체 레코드와 똑같아요. 네이티브는 기존처럼 float로 변환해요.
- 끄는 옵션: `renderer.hbMatrixOnlyUpdates=false`.
- 검사
  - `check-native-matrix-updates`: 움직임·회전·머티리얼 변경·제거·재추가·숨김에서 전체 레코드 방식과 호스트 상태(묶음 멤버 포함 전 그리기와 순서)가 매 프레임 같아요.
  - 가짜 호스트 검사 4종에 같은 처리(`native-mock-draw-transforms.mjs`)를 추가했어요.
- 측정(1만 개 장면, D3D12)
  - 1000개 이동: 렌더 13 → 9.9ms, 물리 27 → 18ms(서브스텝 감소), 프레임 중앙값 41 → 28ms, 전체 레코드 갱신 0개
  - 100개 이동: 실제 화면 562 → 766FPS
  - 정적 장면 3D 0.91ms·2D 0.96ms 유지
- **미검증:** 움직이는 장면의 실제 GPU 픽셀 비교는 아직 없어요(기존 GPU 비교는 정적 장면이에요).
